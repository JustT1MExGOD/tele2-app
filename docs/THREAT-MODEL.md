# Threat Model

> Одна страница: кто может навредить, чему именно, и как. Это дополняет
> [SECURITY.md](./SECURITY.md) (как каждая защита устроена технически) —
> здесь фокус на «от чего мы вообще защищаемся», не на реализации.

## Активы (что можно потерять)

| Актив | Почему важен |
|---|---|
| Данные сотрудников (ФИО, telegram_id, аватар) | PII |
| Продажи/касса/BFQ по сети | Отражает реальные финансовые показатели точки/сети — конкурентно чувствительно между сетями |
| Ролевая модель (`role`, `org_id` на `employees`) | Целостность — кто на что имеет право, кто в какой сети |
| `audit_log` | Подотчётность — если его можно подделать/обойти, вся история действий не заслуживает доверия |
| Доступность бота (единственный `BOT_TOKEN`, 1 реплика) | Основной канал уведомлений сети — простой ломает отчёты/алерты, не просто неудобство |

## Акторы

| Актор | Что может пытаться | Реальная граница |
|---|---|---|
| Аноним в интернете | Дёргать публичные роуты (`/health`, `/access/orgs`, `/access/request`, `/avatars/:id`) | Rate-limit на каждом; ни один не отдаёт чужие бизнес-данные |
| Guest с pending-заявкой | Угадать/подобрать id чужой заявки, посмотреть чужую сеть до одобрения | `effective_org_id`-проверка на approve/reject (см. [SECURITY.md §3](./SECURITY.md#3-авторизация-rbac)) |
| Легитимный `employee`/`senior` одной сети | Заглянуть/повлиять на данные **другой** сети (конкурента внутри той же организации-франшизы) | Org-scope на каждом read/write — самый частый класс реально найденных и исправленных багов в истории проекта (см. [CHANGELOG.md](../CHANGELOG.md)) |
| Легитимный `manager`/`admin` | Назначить себе/другому роль выше положенной; одобрить/отклонить заявку из чужой сети | `canAssignRole()` (строго ниже своей), org-scope на approve/reject |
| Скомпрометированный Telegram-аккаунт легитимного пользователя | Действовать от его имени | Вне контроля этого приложения — безопасность самого Telegram-аккаунта на стороне Telegram/пользователя; initData живёт 1 час, не бессрочно |
| Держатель `BOT_TOKEN` (утечка) | Слать сообщения от имени бота, читать входящие во всех чатах, куда добавлен бот | Токен — секрет уровня «полный контроль над ботом»; ротация — [RUNBOOK.md](./RUNBOOK.md#ротация-bot_token) |
| Держатель `DATABASE_URL` (утечка) | Полный read/write по всем сетям разом — самый широкий блаcт-радиус одного секрета в системе | Нет дополнительного смягчения кроме секретности самой переменной (Railway env) — не хранится в репозитории, не логируется |

## Топ векторов (не гипотетически — из реальной истории проекта)

1. **Cross-tenant утечка данных** — эндпоинт забыл отфильтровать по
   `org_id`. Самый частый класс найденных багов за всю историю (десятки
   фиксов, см. CHANGELOG) — причина, по которой Data Access Layer и
   org-scope тестируются отдельно ([SECURITY.md §3](./SECURITY.md#3-авторизация-rbac), [§5](./SECURITY.md#5-data-access-layer)).
2. **XSS через непроверенный пользовательский текст** в `innerHTML`
   (легаси-фронтенд, классические скрипты без фреймворка) — находились и
   закрывались точечно (последний раз — 20.13.0), не системно
   гарантировано на уровне линтера.
3. **Повторный/задублированный запрос** с реальным побочным эффектом
   (двойная продажа, двойное уведомление, двойной сотрудник) — активная
   работа, не закрыто полностью (см. roadmap 20.15-20.17).
4. **Разведка оргструктуры до аутентификации** — `GET /access/orgs` и
   `GET /access/employees-directory` намеренно публичны (нужны для формы
   регистрации гостя), но это значит, что список названий сетей и
   сотрудников можно получить без входа. Известный, принятый компромисс
   ([SECURITY.md — известные компромиссы](./SECURITY.md#известные-компромиссы)),
   не забытая дыра.
5. **Компрометация единственного секрета** (`BOT_TOKEN` или
   `DATABASE_URL`) — оба дают широкий доступ без дополнительных барьеров
   внутри приложения. Смягчение — операционное (не хранить в репозитории/
   логах, ротация при подозрении), не архитектурное.

## Не в фокусе этой модели

DDoS на инфраструктуру Railway, физическая безопасность устройств
сотрудников, безопасность самого Telegram-клиента — вне контроля этого
приложения и этого документа.
