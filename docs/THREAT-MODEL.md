# Threat Model

> Одна страница: кто может навредить, чему именно, и как. Это дополняет
> [SECURITY.md](./SECURITY.md) (как каждая защита устроена технически) —
> здесь фокус на «от чего мы вообще защищаемся», не на реализации.

## Активы (что можно потерять)

| Актив | Почему важен |
|---|---|
| Данные сотрудников (ФИО, telegram_id, аватар) | PII |
| Продажи/касса/BFQ по сети | Отражает реальные финансовые показатели точки/сети — конкурентно чувствительно между сетями |
| Ролевая модель (`role`, `org_id` на `employees`) | Целостность — кто на что имеет право, кто в какой сети |
| `audit_log` | Подотчётность — если его можно подделать/обойти, вся история действий не заслуживает доверия |
| Доступность бота (единственный `BOT_TOKEN`, 1 реплика) | Основной канал уведомлений сети — простой ломает отчёты/алерты, не просто неудобство |

## Акторы

| Актор | Что может пытаться | Реальная граница |
|---|---|---|
| Аноним в интернете | Дёргать публичные роуты (`/health`, `/access/orgs`, `/access/request`, `/avatars/:id`) | Rate-limit на каждом; ни один не отдаёт чужие бизнес-данные |
| Guest с pending-заявкой | Угадать/подобрать id чужой заявки, посмотреть чужую сеть до одобрения | `effective_org_id`-проверка на approve/reject (см. [SECURITY.md §3](./SECURITY.md#3-авторизация-rbac)) |
| Легитимный `employee`/`senior` одной сети | Заглянуть/повлиять на данные **другой** сети (конкурента внутри той же организации-франшизы) | Org-scope на каждом read/write — самый частый класс реально найденных и исправленных багов в истории проекта (см. [CHANGELOG.md](../CHANGELOG.md)) |
| Легитимный `manager`/`admin` | Назначить себе/другому роль выше положенной; одобрить/отклонить заявку из чужой сети | `canAssignRole()` (строго ниже своей), org-scope на approve/reject |
| Скомпрометированный Telegram-аккаунт легитимного пользователя | Действовать от его имени | Вне контроля этого приложения — безопасность самого Telegram-аккаунта на стороне Telegram/пользователя; initData живёт 1 час, не бессрочно |
| Держатель `BOT_TOKEN` (утечка) | Слать сообщения от имени бота, читать входящие во всех чатах, куда добавлен бот | Токен — секрет уровня «полный контроль над ботом»; ротация — [RUNBOOK.md](./RUNBOOK.md#ротация-bot_token) |
| Держатель `DATABASE_URL` (утечка) | Полный read/write по всем сетям разом — самый широкий блаcт-радиус одного секрета в системе | Нет дополнительного смягчения кроме секретности самой переменной (Railway env) — не хранится в репозитории, не логируется |

## Топ векторов (не гипотетически — из реальной истории проекта)

1. **Cross-tenant утечка данных** — эндпоинт забыл отфильтровать по
   `org_id`. Самый частый класс найденных багов за всю историю (десятки
   фиксов, см. CHANGELOG) — причина, по которой Data Access Layer и
   org-scope тестируются отдельно ([SECURITY.md §3](./SECURITY.md#3-авторизация-rbac), [§5](./SECURITY.md#5-data-access-layer)).
   Один подтверждённый пример без исправления: `GET /supervisor/stores`
   (ветка manager/admin) отдаёт точки всех сетей без org-фильтра — принято
   как есть, зафиксировано в [SECURITY.md — известные компромиссы](./SECURITY.md#известные-компромиссы).
2. **XSS через непроверенный пользовательский текст** в `innerHTML`/
   `onclick="..."` — находились и закрывались точечно (последний раз —
   20.49.0, включая attribute-breakout класс), не системно гарантировано
   на уровне линтера (`check-dangerous-js-patterns.mjs` намеренно не
   проверяет `innerHTML`/`onclick=` эвристикой). Несколько подтверждённых
   мест вне охвата 20.49.0 остаются незакрытыми — см.
   [SECURITY.md — известные компромиссы](./SECURITY.md#известные-компромиссы).
3. **Повторный/задублированный запрос** с реальным побочным эффектом
   (двойная продажа, двойное уведомление, двойной сотрудник) — закрыто на
   критичных write-путях (`client_id`-идемпотентность, 20.15.0/20.50.0),
   не универсально для всего API.
4. **Разведка оргструктуры до аутентификации** — `GET /access/orgs` и
   `GET /access/employees-directory` намеренно публичны (нужны для формы
   регистрации гостя), но это значит, что список названий сетей и
   сотрудников можно получить без входа. С 20.50.0 — под rate-limit
   30/мин (раньше вообще без лимита). Известный, принятый компромисс
   ([SECURITY.md — известные компромиссы](./SECURITY.md#известные-компромиссы)),
   не забытая дыра.
5. **Компрометация единственного секрета** (`BOT_TOKEN` или
   `DATABASE_URL`) — оба дают широкий доступ без дополнительных барьеров
   внутри приложения. Смягчение — операционное (не хранить в репозитории/
   логах, ротация при подозрении), не архитектурное.

## Угрозы, специфичные для браузера/PWA (Web Security & Trust Layer)

С появлением browser/PWA-входа (20.35.0-20.48.0) модель угроз шире, чем
только Telegram-канал. Формат: Угроза → Существующие контроли → Остаточный
риск → Планируемое улучшение — не писать «mitigated», если остаточный риск
реален.

| Угроза | Существующие контроли | Остаточный риск | Планируемое улучшение |
|---|---|---|---|
| Кража browser-сессии (украден токен из cookie/устройство) | `httpOnly`+`Secure`(прод)+`SameSite=lax` на `t2_session`; явный список/отзыв сессий (`GET/DELETE /auth/sessions`) | Абсолютный TTL 30 дней без idle-таймаута — украденная активная сессия рабочая весь этот срок, если жертва не заметит и не отзовёт вручную | Idle-таймаут (см. [SECURITY.md roadmap](./SECURITY.md#security-roadmap--целевой-профиль)) |
| CSRF на изменяющих запросах с cookie | Double-submit (`t2_csrf`) + `Sec-Fetch-Site`/`Origin`-слой (20.48.0) | `/auth/login`/`/register`/`/reset/:token` намеренно исключены (см. [SECURITY.md §1](./SECURITY.md#1-периметр)) — обоснованно, но это осознанная граница, не «CSRF закрыт везде» | — |
| XSS → кража сессии/CSRF-токена | `httpOnly` на `t2_session` (сам токен сессии не читается скриптом даже при XSS); `esc()`-дисциплина на большей части вывода; 4 конкретных raw-sinks, найденных документационным аудитом, закрыты в 20.50.1 | `t2_csrf` намеренно НЕ `httpOnly` (double-submit того требует) — успешный XSS может прочитать его и подделать запрос от имени жертвы; `check-dangerous-js-patterns.mjs` не гейтит `innerHTML`/`onclick=` эвристикой (см. SECURITY.md) — новый недоэкранированный sink не будет пойман автоматически | Строгий CSP без `unsafe-inline` (roadmap) закрыл бы этот класс структурно, не точечно |
| Credential stuffing / brute force на `/auth/login` | Лимит 10/мин по `sha256(normalizePhone(phone))`, не по IP — закрывает распределённый перебор одного номера через много IP; работает поверх общего 300/мин-по-IP | Нет отдельной временной блокировки аккаунта после N неудач подряд (только rate-limit по времени) | Отдельный порог + временная блокировка на `/auth/*` (см. SECURITY.md roadmap) |
| Коллизия/угон телефон-identity | `bindIdentityStrict()` — конфликт с чужим номером даёт явный `409`, transfer не разрешён (телефон — credential boundary, не recovery) | Нет — семантика уже строгая по конструкции | — |
| Злоупотребление Telegram identity transfer (steal) | Атомарный `INSERT...ON CONFLICT` (race-safe), это осознанный self-service recovery flow, не баг | Кто угодно, кто провёл валидный Telegram-логин под тем же `telegram_id`, легитимно «крадёт» привязку — это заявленный продуктовый инвариант (владение Telegram-аккаунтом = владение привязкой), не путать с уязвимостью | — |
| Cross-tenant IDOR/BOLA через browser-роуты | Тот же `orgId`-обязательный DAL-паттерн, что для Telegram-пути — browser-сессия не создаёт отдельный, менее строгий путь к данным | Один известный пробел (`GET /supervisor/stores`, см. выше) | — |
| Сессия переживает деактивацию/сброс пароля | Деактивация и `/auth/reset/:token`/`/me/link-phone` немедленно отзывают все `employee_sessions` (20.48.0) | Нет — закрыто транзакционно | — |
| Подмена IP / proxy spoofing для rate-limit | `trustProxy: 1` — доверяем ровно одному ожидаемому хопу Railway, не произвольной `X-Forwarded-For`-цепочке | Топология Railway (ровно один hop) — предположение о деплое, не подтверждённое кодом; при смене инфраструктуры требует пересмотра | — |
| Компрометация admin-аккаунта | `canAssignRole()` — только admin может выдать роль admin; `audit_log` фиксирует `actor_role`/`before`/`after` на смену роли; **20.52.0** — WebAuthn/TOTP/recovery codes (ADR-009), channel-agnostic step-up на выдачу admin/сброс чужого пароля/MFA; **20.52.1** — украденный только пароль больше не даёт вообще НИКАКОГО privileged-доступа (не только опасных действий), если у аккаунта нет MFA — `requireActive()` блокирует всё, кроме enrollment, `403 mfa_enrollment_required` (см. ADR-009 revision) | Самопонижение без второго admin в сети технически необратимо через UI (см. [RUNBOOK.md](./RUNBOOK.md#восстановление-доступа-admin)); полноценная WebAuthn browser-ceremony UI отложена (TOTP-путь закрывает mandatory-политику) | WebAuthn browser UI (см. SECURITY.md roadmap) |
| Обход/отсутствие MFA у privileged-аккаунта (украден пароль, но не второй фактор) | **20.52.1** — mandatory больше не ограничивается step-up-gated действиями: login-time второй фактор остаётся свойством аккаунта, но `requireActive()` (auth/guards.ts) блокирует ЛЮБОЙ защищённый роут для admin/supervisor без фактора, кроме enrollment/status/logout; сброс пароля (`POST /auth/reset/:token`) тоже больше не выдаёт сессию в обход MFA (RESET-1); эскалация роли отзывает существующие сессии, чтобы старая AAL1-сессия не унаследовала privileged-доступ (ROLE-1) | Recovery-code brute force ограничен только общим rate-limit'ом (20/мин на `/auth/mfa/*`), нет отдельной временной блокировки аккаунта после N неудачных попыток | Временная блокировка после N неудачных MFA-попыток (см. SECURITY.md roadmap) |
| Supply-chain компрометация зависимости/CI | `npm audit --audit-level=high` как gate CI | Нет SAST/secret-scanning/пиннинга GitHub Actions по SHA | См. [SECURITY.md roadmap](./SECURITY.md#security-roadmap--целевой-профиль) |
| Вредоносный/скомпрометированный браузерный клиент | Сервер — единственная граница допуска (baseline-принцип #2), клиент никогда не доверенная сторона | Не специфично для browser-канала — тот же принцип, что уже применялся к Telegram-клиенту | — |

## Угрозы криптографическому слою данных (Level 2, 20.51.0)

Формат: Угроза → Существующие контроли → Остаточный риск → Recovery.
Полный разбор устройства слоя — [SECURITY.md — Cryptographic Data
Protection](./SECURITY.md#10-cryptographic-data-protection),
[docs/DATA-SECURITY-ARCHITECTURE.md](./DATA-SECURITY-ARCHITECTURE.md).

| Угроза | Существующие контроли | Остаточный риск | Recovery |
|---|---|---|---|
| Кража/утечка дампа БД (backup, реплика, диск) | `support_tickets.message`/`admin_reply`, `support_messages.body` — application-level envelope encryption (AES-256-GCM); дамп содержит только ciphertext+метаданные конверта | Все остальные таблицы (sales/plans/employees/audit_log/...) остаются plaintext в дампе — это осознанная граница (см. [DATA-SECURITY-ARCHITECTURE.md](./DATA-SECURITY-ARCHITECTURE.md)), не полное at-rest шифрование БД | Ротация KEK не спасает от уже случившейся утечки текущего KEK — только предотвращает расшифровку БУДУЩИХ дампов тем же скомпрометированным ключом |
| Злонамеренный/скомпрометированный DB-оператор (read-доступ к диску/бэкапу, не к работающему приложению) | То же, что выше — оператор с доступом только к БД не видит содержимое зашифрованных полей без отдельного доступа к `ENCRYPTION_KEKS` (env, не в PostgreSQL) | Оператор с доступом и к БД, и к env переменным приложения (полный компромисс сервера) видит всё — Level 2 не защищает от этого, это Level 3 (E2EE) сценарий, см. ADR-008 | — |
| Компрометация работающего backend-процесса (RCE, скомпрометированная зависимость) | Нет — Level 2 расшифровывает по требованию, скомпрометированный процесс имеет доступ к KEK так же, как легитимный код | Полный — это именно то отличие Level 2 от Level 3, задокументированное честно (не заявляем защиту, которой нет) | Ротация KEK + аудит затронутых записей после инцидента |
| Перенос ciphertext одной записи в колонку другой (DB-level tampering, не через API) | AAD связывает ciphertext с `{type, id, ...}` конкретной строки (§6) — `AEAD tag` не сходится, `decryptField()` бросает `DecryptionError` | Обнаруживается только при следующем чтении, не проактивно (нет фонового сканера целостности) | Логируется как `envelope decrypt failed` (`errorClass`, без содержимого) — сигнал для ручного расследования |
| Потеря/уничтожение `ENCRYPTION_KEKS` (все версии) | Нет — честно, никакого скрытого master recovery key не существует (§31 инвариант) | Зашифрованные записи невосстановимы навсегда | Резервное хранение `ENCRYPTION_KEKS` — операционная процедура вне кода (Railway env backup/secrets manager), не описана этим документом как готовая |
| MITM подмена публичного ключа устройства | N/A | N/A — нет device identity/handshake (см. ADR-008), угроза неприменима к текущей архитектуре | — |
| Compromised message key / ratchet state | N/A | N/A — нет ratchet (см. ADR-008) | — |
| Downgrade E2EE → plaintext | N/A для Level 2 (флаг гейтит только новые записи, чтение старых зашифрованных строк не зависит от флага — см. SECURITY.md §10) | Не применимо к Level 3, которого нет | — |
| Metadata leakage (кто/кому/когда/сколько) | Level 2 не скрывает метаданные тикета (`employee_id`, `created_at`, `category`, размер) — только содержимое `message`/`admin_reply`/`body` | Реальный, честно задокументированный остаточный риск — тот же принцип, что §23 исходного крипто-брифа: «server knows metadata» не должно писаться как «server knows nothing» | — |

## Не в фокусе этой модели

DDoS на инфраструктуру Railway, физическая безопасность устройств
сотрудников, безопасность самого Telegram-клиента — вне контроля этого
приложения и этого документа.
