# Desktop Design

Информационная архитектура, design-система и responsive-стратегия для
desktop, принятые владельцем продукта перед 20.40. Основано на
[DESKTOP-UX-AUDIT.md](./DESKTOP-UX-AUDIT.md). 20.40 реализует IA-правки +
design-систему + полный редизайн Home; остальные страницы — staged
roadmap ниже, код не тронут в 20.40.

## Информационная архитектура

Ширина сайдбара, шипнутого в 20.39, остаётся прежней (решение осознанное,
не недосмотр — см. "Реальность доступа" в аудите: почти все страницы
видны всем, гейтить секции по роли корректно ложится только на
небольшую часть). Три правки к уже реализованному 20.39-сайдбару:

- **Обзор** (всегда): Главная · **Профиль** *(переименовано из "Мой
  план" — на мобильном тот же `data-page="my"` всегда назывался
  "Профиль", сайдбар был единственным местом с другим именем той же
  страницы)* · Задачи · График · **Команда** *(перенесено из
  "Управление" — страница не гейтится (`team.ts` гейтит только
  `.managerTools`-панель внутри), на мобильном permanент в bottom-nav;
  гейтить её в сайдбаре было регрессией — обычный сотрудник терял вход
  именно на desktop)*
- **Аналитика** (`canViewAnalytics()`): Command Center
- **Управление** (`canManage()`): Касса
- **Супервайзер** (`isSupervisor()||canAdmin()`): Обзор/Точки/Люди/Тренд
- **Администрирование** (`canAdmin()`): Сети/Аудит

~15 "инструментальных" страниц без своей записи в навигации (bfq,
monthplan, netmonth, heatmap, forecast, announce, reportimg, live,
support, alerts, reports, history) остаются достижимы так же, как на
мобильном — через список "Инструменты" на Главной. Не расширяем сайдбар
на них в этом заходе — если конкретный будущий редизайн страницы (напр.
Command Center) даст веский повод, пересмотрим точечно.

## Топбар

Из растянутого мобильного header — в рабочую панель с контекстом
страницы:

- **Слева** — breadcrumb/заголовок страницы, выводится из того же `name`,
  что уже приходит в `switchPage()`/уже есть как текст в
  `.sidebar-title`/label — без нового источника данных
- **Центр** — пустой layout-слот, зарезервирован под будущий command
  palette (20.41+, по существующей заметке в changelog); никакого
  fake-поиска
- **Справа** — существующие `#userAvatar`, переключатель темы, refresh,
  `#headerDate`, `#headerStorePill` — без изменений, просто
  перепозиционированы в новую раскладку

## Design-система (примитивы)

Добавляются в существующий `@media (min-width: 860px)` блок
`styles.css` — один файл, без per-page CSS (закреплено ADR-006 и
дисциплиной каждой прошлой версии). Опираются только на уже существующие
токены (ничего нового не вводится без явной причины):

| Класс | Назначение | Механизм |
|---|---|---|
| `.page-header` | заголовок страницы + `.page-actions` справа | flex, `padding:var(--sp-4) 0`, `border-bottom:1px solid var(--border)` |
| `.page-actions` | кластер кнопок действий | flex, `gap:var(--sp-2)`, переиспользует `.btn-main`/`.btn-ghost` |
| `.workspace-grid` | N карточек/панелей рядом с переносом | `grid-template-columns:repeat(auto-fit,minmax(320px,1fr))`, `gap:var(--sp-4)` — по образцу уже responsive `.hm-grid` (`auto-fill`) |
| `.metric-grid` | KPI/stat-строка | обобщение `.stats-row` на `auto-fit`, не захардкожено на 3 колонки |
| `.row--dense` | модификатор существующего `.row` для плотных desktop-списков | не отдельный компонент — одна абстракция, не два параллельных list-паттерна |

**Motion/a11y**: только существующие `--dur-fast/base/slow` +
`--ease`/`--ease-out` — ничего в этом заходе не трогает жесты/пружины
(`createSpring()`), `prefers-reduced-motion` не меняется.

**Осознанно не строится сейчас** (нет потребителя — тот же принцип, что
уже отклонял неиспользуемый 1600px-tier/`.data-table`/`.modal-xl` в
20.39): `.data-table` (первая реальная потребность — Team, 20.41),
`.detail-panel`, `.desktop-toolbar`.

## Responsive-стратегия

Два существующих shell-уровня не трогаются: `<860px` — мобильный,
`≥860px` — shell (сайдбар/топбар), `≥1200px` — шире колонка `.sheet`
(800→1120px).

**Дашборд Главной получает свой отдельный порог: `≥1200px`, не `≥860px`.**
В диапазоне 860–1199 shell-хром (сайдбар+топбар) уже виден, но
*контент* Главной — тот же мобильный swipe-каталог (карусель, точки,
одна колонка), просто внутри более широкой `.sheet`. Двухколоночный
дашборд, втиснутый в 860-1199px, читался бы сжато — вместо этого он
появляется только на `≥1200px`, переиспользуя уже существующий второй
tier, а не вводя новое одноразовое значение брейкпоинта (860/1200/1600
остаётся 3-значной шкалой, не 4).

**`≥1600px`** — только для сетки дашборда Главной (не глобальный tier):
3-я колонка появляется, только если панель аналитики реально
отрендерена в DOM (см. ниже), не по одной лишь роли — иначе у сотрудника
без `canViewAnalytics()` была бы пустая треть экрана.

## Модальная стратегия

Без изменений — `.modal-sm/md/lg` (20.39) остаются достаточными для
20.40 (нет ни одного нового потребителя большого модального окна в
этом заходе). `.modal-xl` не вводится, пока не появится настоящий
потребитель (первый кандидат — вероятно, Team, 20.41+).

## Табличная стратегия

Единственный настоящий `<table>` (`.sum-sch-table`) остаётся как есть.
Общий `.data-table`-примитив — не в этом заходе (см. выше); появится
вместе с первой страницей, которой он реально нужен (Team, 20.41),
спроектированный под реальную задачу (сортировка колонок — новая
интеракция без прецедента в кодовой базе), не заранее "на вырост".

## Home / Dashboard — реализация 20.40

**Архитектурное решение** (фиксирует урок, уже дважды стоивший бага в
этой сессии): десктопный дашборд Главной — **новая разметка**, не
CSS-grid поверх мобильного swipe-DOM. `.swipe-track{display:grid
!important}` — механизм, ответственный за оба переполнения
20.39.0/20.39.1 (`initSwipePanels()`'s `settle()` продолжал писать инлайн
`height`/`transform` поверх CSS-переопределения). Переиспользовать
интерактивный мобильный DOM под неинтерактивную десктопную раскладку —
хрупко по конструкции; чище — не делить DOM для этого раздела вообще.

`#homeTodaySwipe` остаётся **полностью нетронутым ниже 1200px** — тот же
DOM, тот же жест, мобильные пользователи и диапазон 860-1199 не видят
изменений. Новая секция `.desktop-dashboard` показывается только на
`≥1200px` (`display:none` вне медиа-запроса — тот же паттерн, что уже
использует `.sidebar`), наполняется расширением уже существующих
`loadHome()`/`loadMyDay()` — данные (`getMyDay`, `getStatsDaily`,
`getSupervisorHealth`) получены один раз, два тонких render-хелпера их
потребляют (один для мобильных swipe-панелей, один для десктопного
дашборда) — ни одного нового API-вызова, backend не тронут.

**Без дублирования chrome**: топбар уже показывает "Главная" и уже имеет
кнопку refresh — `.desktop-dashboard` не получает свой `.page-header` со
вторым заголовком/refresh, начинается сразу с `.metric-grid`.

Структура:
```
.metric-grid            — KPI: % выполнения плана за сегодня (getMyDay),
                           сетевые итоги (home stats)
.workspace-grid (2-up)  — Мой день | Сеть сегодня (постоянно рядом,
                           реальные данные, без карусели)
.workspace-grid (2-up)  — План/прогресс | Alerts/insights
                           (панель аналитики — canViewAnalytics(),
                           переиспользует данные commandCenterSection)
.row.row--dense список  — вторичные инструменты (тот же контент, что
                           мобильный список "Инструменты")
```
На `≥1600px` grid аналитики переходит на 3 колонки **только если панель
аналитики реально в DOM** — `:has()`-правило
(`.workspace-grid:has(.insights-panel){grid-template-columns:repeat(3,1fr)}`),
завязанное на собственный класс панели, не на роль напрямую (решение
между `:has()` и JS-классом принимается при реализации, фиксируется одной
фразой в changelog — не оба варианта параллельно).

**Swipe не должен исполняться вообще, когда активен дашборд** —
раздельного DOM недостаточно (скрытый `.swipe-track`, в который
`initSwipePanels()` продолжает писать `height`/`transform` при
resize/асинхронной подгрузке — та же природа бага, что уже дважды
находили). Один общий guard на `window.innerWidth >= 1200` (порог
дашборда, не порог shell 860px), применённый во всех точках входа,
способных писать в track: начальный `settle(0,false)`, обработчик
`touchstart` (ранний return), `resize`-слушатель, `_swipeRefreshHeight()`
(вызывается после асинхронной подгрузки данных). Ниже 1200 — no-op,
swipe ведёт себя как сегодня, включая диапазон 860-1199. Существующие
guard'ы 20.39.0/20.39.1 (на 860, добавленные именно против этого же
конфликта) **заменяются** этим единым guard'ом на 1200, не остаются
рядом вторым слоем.

`.swipe-track`'s desktop `display:grid !important` полностью убирается —
ниже 1200 track должен выглядеть и вести себя как на мобильном, выше
1200 — скрыт, никогда не нужен одновременно "виден и должен быть grid".
