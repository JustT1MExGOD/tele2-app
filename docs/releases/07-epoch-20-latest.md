## 20.40.0

**Design Системные маршруты + Home Dashboard — первая настоящая страница поверх Desktop Shell.** Владелец продукта прислал развёрнутый бриф на полную переделку desktop UX всего приложения (~30 страниц), явно потребовав аудит ДО кода и запретив начинать массовый рефакторинг без review. Процесс: сначала `docs/DESKTOP-UX-AUDIT.md` — полная инвентаризация каждой страницы (кто видит, какие данные, текущий UI-паттерн, покрытие desktop-CSS); ключевой находкой стало то, что почти каждая страница видна ВСЕМ ролям, а гейтится обычно не доступ к странице, а запись/редактирование внутри неё (`canManage()` прячет кнопки, не саму страницу) — это меняет то, как проектировать IA (нельзя просто гейтить целые секции сайдбара по роли, как это сделал 20.39 для малого набора пунктов).

Затем `docs/DESKTOP-DESIGN.md` — предложенная IA, design-система, responsive-стратегия, staged план развития по страницам. Owner review плана (через `EnterPlanMode`) дал 10+ конкретных технических уточнений, все приняты до кода. Согласованный скоуп реализации — ровно design-система + Home, ничего больше: `docs/DESKTOP-UX-AUDIT.md`+`docs/DESKTOP-DESIGN.md` → CSS-примитивы (`.page-header`/`.page-actions`/`.workspace-grid`/`.metric-grid` — все `auto-fit` по образцу уже responsive `.hm-grid`, не захардкоженные колонки как у `.stats-row`; `.row--dense` — модификатор существующего `.row`, не второй параллельный list-компонент "на вырост"; `.data-table`/`.detail-panel`/`.desktop-toolbar` сознательно не заведены — ни одной странице в этой версии не нужны) → разметка Home → JS-рендер → guard'ы `initSwipePanels()` в последнюю очередь.

Team/Schedule/Command Center/Supervisor/Admin — staged пункты 20.41-20.44 в самом план развития-документе, код этих страниц не тронут ни строкой. Три мелких, но реальных бага, найденных по пути (тот же класс проблем, что уже несколько раз всплывал в 20.35-20.39: остатки Telegram-only допущений и рассинхрон mobile/desktop меток), отдельным абзацем от новой архитектуры: (1) сайдбар называл `data-page="my"` "Мой план", хотя тот же самый пункт на мобильном всегда назывался "Профиль" — переименовано; (2) "Команда" была гейтед `canManage()` в сайдбаре, хотя `team.ts` гейтит только внутреннюю `.managerTools`-панель, не саму страницу, а на мобильном пункт постоянный в bottom-nav — обычный сотрудник терял вход в "Команда" именно на десктопе, перенесено в "Обзор" (всегда видимая секция); (3) `loadMyDay()` безусловно делал ранний return по `!tgUser()?.id` — стало неверным ещё с 20.35 (не-Telegram вход): `GET /me/day` и так уже гейтится по identity независимо от провайдера и graceful возвращает `{bound:false, message:'Привяжите аккаунт во вкладке Профиль'}` (сам текст сообщения уже предполагал имя "Профиль" — ещё одно подтверждение находки №1), старый гейт молча ломал "Мой день" для ЛЮБОГО desktop/phone-login сотрудника.

Архитектурное решение для Home, исправляющее сам источник обоих багов 20.39.0/20.39.1: десктоп-дашборд — НЕ CSS-grid поверх мобильного swipe-DOM (`.swipe-track{display:grid!important}` трижды подряд конфликтовал с `initSwipePanels()`), а отдельная разметка (`.desktop-dashboard`, `#page-home`), populated расширением тех же `loadHome()`/`loadMyDay()` — данные получены один раз (`getMyDay`/`getStatsDaily`/`getSupervisorHealth`), два тонких render-таргета (`setBothHTML()`) их потребляют, ни одного нового API-вызова, backend не тронут. Порог дашборда — отдельный от порога shell: `≥1200px`, не `≥860px` (владелец лично поправил первую версию плана после review) — в диапазоне 860-1199 виден shell (сайдбар+топбар), но контент Главной остаётся мобильным swipe-каталогом без изменений: насильно втиснутый в узкий ноутбучный экран двухколоночный дашборд читался бы хуже мобильного layout внутри просто более широкой колонки.

Swipe должен не исполняться вообще, когда активен дашборд, а не просто быть визуально перебит CSS — раздельного DOM недостаточно, `settle()` продолжал бы писать инлайн `height`/`transform` в скрытый track при каждом resize/асинхронной подгрузке (тот же класс бага, что уже дважды находили). Guard'ы 20.39.0/20.39.1 (порог 860px) **заменены** (не оставлены рядом вторым слоем) одним guard'ом на `SWIPE_DESKTOP_BREAKPOINT=1200` внутри `settle()` — идемпотентная проверка перед записью (реально ноль обращений к `style` после первого сброса, не просто "пишем пустую строку каждый раз"), тот же порог в `touchstart`.

Проверено живым Playwright: на 1199 drag/dots работают как раньше, на 1200 — нет; `.swipe-track` не получает ни одной инлайн-записи через init+resize+асинхронный рефреш подряд. `.swipe-track{display:grid!important}` в CSS полностью убран — ниже 1200 выглядит как мобильный, выше скрыт целиком, никогда не нужно одновременно. Топбар получил breadcrumb (`#topbarBreadcrumb`, текст — из уже существующей подписи активного `.sidebar .nav-item` в `switchPage()`, не новый источник данных) — и сразу же живым скриншотом на 1200px пойман реальный дубль: мобильная секция `#commandCenterSection` ("Сеть за минуту") не была скрыта на десктопе и рендерила ту же health-score карточку, что и новая `.desktop-dashboard`'s панель аналитики, дважды на одной странице; закрыто тем же приёмом, что уже был у `.bottom-nav` в 20.39.0 (`!important` поверх инлайн-`display`, который `loadCommandCenter()` ставит независимо на обе секции).

Изначальный план предполагал 3-колоночную сетку "Топ за 7 дней"/"Аналитика" на `≥1600px` через `:has(.insights-panel)` — при живой проверке выяснилось, что эта секция структурно вмещает максимум 2 панели вообще, ни для одной роли нет третьего контент-блока, поэтому `repeat(3,1fr)` создавал пустую 3-ю колонку ВСЕГДА, когда аналитика показана — ровно то, чего пункт должен был избежать, просто для другой роли; убран, не заменён — на ultrawide `auto-fit` из design-системы просто даёт панелям больше ширины честно, без фиктивного места (класс `.insights-panel` остаётся в JS на будущее, если появится настоящий 3-й блок).

Отдельно обнаружен и обойдён rate-limiter собственного дев-сервера (300 запросов/60с, `x-ratelimit-*` заголовки) — Playwright-матрица из 10 ширин исчерпывала лимит на девятом-десятом полном перезаходе страницы (каждый — HTML+CSS+23 JS-бандла); не баг продукта, особенность верификации в этом окружении, скриншоты досняты после сброса окна. Верификация — полная матрица 390/768/859/860/1024/1199/1200/1440/1600/1920px живым Playwright: мобильный Home на 859 пиксель-в-пиксель прежний; 860-1199 показывает shell поверх немодифицированного мобильного контента, не "полу-дашборд"; ровно один "Главная" и один refresh на десктопе; сотрудник без `canViewAnalytics()` не видит пустой колонки на 1920px (панель аналитики просто отсутствует в DOM, сосед занимает всю ширину через `auto-fit`). 360 → 363 фронтенд-теста (`home-page.test.ts` расширен: `setBothHTML()`-зеркалирование в оба render-таргета, `.insights-panel` toggle на успех/ошибку/без-прав, идемпотентное клонирование `#homeToolsSection` → `#homeDesktopTools` без дубля `id`), `tsc --noEmit` (backend+frontend)/`smoke:frontend`/`check:no-direct-sql` зелёные

Плюс: остаточная пустая область под "Сеть сегодня"/"Топ за 7 дней" всё ещё оставалась даже с `align-items:start` (grid-строка остаётся высотой самой высокой ячейки) — `.workspace-col`, независимые вертикальные колонки вместо парных строк, настоящая masonry-независимость. Плюс: `.sheet` 1120px-кап (откалиброван под однострочный контент остальных страниц в 20.39) читался как большая пустая область справа для реального workspace-grid — `.sheet:has(#page-home.active)` расширяет до 1440px/1600px только для Home, остальные страницы не тронуты. `20.40.3` — мобильные секции "Калькуляторы"/"Топ за 7 дней"/"Инструменты" оставались видимыми на десктопе НИЖЕ дашборда, хотя тот же контент уже рендерился внутри него — визуальный дубль каждой; скрыты на ≥1200px (тот же приём, что `#commandCenterSection` в 20.40.0). ## 20.40.1

**Хотфикс по живым прод-данным сразу после 20.40.0.** Владелец продукта прислал скриншот реального desktop-дашборда — на настоящих данных (точка "Мегалит", полный набор из 10 отслеживаемых метрик: SIM/MNP/ПА/Комбо/Тел/Доп/Страх/Wink/ШПД/ФО) карточка "Мой день" оказалась заметно выше своей пары "Сеть сегодня" в том же `.workspace-grid`, а CSS Grid по умолчанию (`align-items:stretch`) растягивал короткую карточку под высоту длинной — большая пустая белая область снизу "Сеть сегодня" (и аналогично у пары "Топ за 7 дней"/"Сеть за минуту").

Синтетические Playwright-фикстуры из 20.40.0 использовали всего 6 метрик и не воспроизводили эту разницу высот — баг проявился только на реальном объёме данных одной конкретной точки, не на тестовых заглушках. Один атрибут — `.workspace-grid { align-items: start }` — обе панели теперь по высоте собственного контента, ровный верх, разный (честный) низ, вместо разной высоты потенциально с большой пустой областью. Проверено живым Playwright с реплицированным сценарием (10 прогресс-баров в "Мой день" против короткой "Сеть сегодня") — пустая область исчезла на скриншоте.

Чисто CSS, JS/разметка не тронуты, 363 фронтенд-теста без изменений, `tsc --noEmit`/`smoke:frontend` зелёные — без анонса в Telegram-чат (хотфикс, не эпик)

## 20.40.2

**Хотфикс по живому прод-скриншоту с ролью admin — реальный access-баг, найденный за пределами заявленного 20.40 CSS-only скоупа.** Владелец продукта прислал скриншот реального desktop-дашборда, залогинившись как admin — сайдбар показывал только секцию "Обзор", ни "Аналитика", ни "Управление", ни "Супервайзер", ни "Администрирование" не появлялись вообще. Расследование нашло причину не в CSS и не в 20.40: `gateSidebarSection()`-вызовы (введены в 20.39.0) жили только внутри Telegram-ветки `bootApp()` (`access-supervisor/index.ts`) — не-Telegram bound-ветка (desktop-браузер/`POST /auth/login` через телефон, механизм с 20.35+) делала `return` через `enterHomeOrSupervisorShell()` РАНЬШЕ этого кода; то же верно для 404-резервный вариант-ветки (`/access/status` не найден) и для catch-ветки при сетевой ошибке — итого 3 из 4 путей выхода из `bootApp()` никогда не гейтили секции сайдбара вообще, независимо от реальной роли пользователя.

Тот же класс бага, что уже чинили в `loadMyDay()` в 20.40.0 (Telegram-only допущение, протухшее с приходом multi-provider auth в 20.35, просто не пойманное раньше, потому что вся верификация 20.39/20.40 до этого момента байпасила `bootApp()` синтетической подстановкой `window.me`, а не гоняла реальный boot flow). Исправлено: 4 повторяющихся блока (`btnAccessRequests`/`btnSupervisor`/`btnMgrTutorial` + 4 `gateSidebarSection()`) вынесены в одну `applyRoleGatedNav()`, вызывается из всех 4 веток `bootApp()` — не-Telegram/404/success/catch. Проверено не синтетической подменой `window.me`, а полным живым прогоном `bootApp()` с мокнутым `fetch()` (`/me`, `/access/status`, `/me/day`, `/supervisor/health`) — ровно тот код, что реально исполняется в браузере пользователя; 2 новых теста в `access-supervisor-page.test.ts` (не-Telegram admin — все 4 секции открыты; не-Telegram employee — все 4 остаются скрыты), 363 → 365.

Заодно, в том же живом скриншоте, ещё два реальных находки по layout: (1) даже с `align-items:start` (20.40.1) под короткой панелью в паре ("Сеть сегодня"/"Топ за 7 дней") оставалась пустая область — align-items управляет положением ВНУТРИ grid-строки, а не высотой самой строки, которая остаётся высотой самой высокой ячейки; заменено на `.workspace-col` — независимые вертикальные flex-колонки вместо парных grid-строк, каждая складывает свои панели по своей собственной высоте, без общей высоты с соседней колонкой вообще (настоящая masonry-независимость, не имитация выравниванием); (2) `.sheet{max-width:1120px}` (откалиброван в 20.39 под однострочный mobile-style контент остальных страниц, "нормально, если хочешь сохранить читаемость") на реальном многоколоночном workspace-grid-контенте читался как большая пустая область справа, не запас — `.sheet:has(#page-home.active){max-width:1440px}` на ≥1200px и `1600px` на ≥1600px, гейтится `:has()` только на активную страницу Home, остальные страницы (вне scope 20.40) не тронуты, тот же `.sheet{1120px}` у них как был.

Проверено живым Playwright на 1200/1440/1920 (полный boot flow с мокнутым fetch, не синтетический байпас) и мобильным 859 (без изменений). `tsc --noEmit` (backend+frontend)/`smoke:frontend` зелёные — без анонса в Telegram-чат (хотфикс, не эпик, хоть и существенный по содержанию)

## 20.40.3

**Хотфикс — визуальный дубль трёх секций Home на десктопе.** Владелец продукта: "почему блок Инструменты дублируется? убери это. и блок с калькуляторами помести под сеть за минуту". Причина: `.desktop-dashboard` (20.40.0) рендерит "Топ за 7 дней" в свой собственный `#homeTopDesktop` и клонирует "Инструменты" в `#homeDesktopTools` — но ОРИГИНАЛЬНЫЕ мобильные секции `#homeTop`/`#homeToolsSection` никогда не скрывались на ≥1200px (в отличие от `#homeTodaySwipe`/`#commandCenterSection`, которые скрыли ещё в 20.40.0) — оставались видимыми НИЖЕ дашборда, тот же контент дважды на одной странице. **Web Security & Trust Layer, часть 1 — Authentication & Session Security.** Со standalone iPhone Web App/Safari-слоем (20.47.0) у приложения де-факто три канала входа — Telegram Mini App, телефон-браузер, standalone PWA — вместо одного доверенного Telegram-канала, на котором строилась исходная модель угроз. Аудит кода (не догадки) показал, что многое уже построено: провайдер-агностичная `Identity`/`Principal`-граница (ADR-005), реальная cookie-сессия для phone-входа (`employee_sessions`, `HttpOnly+Secure+SameSite=Lax`, только `sha256(token)` в БД), rate-limit на чувствительных роутах, уже throttled `last_seen_at` (раз в час, `touchSession()`), уже свежая генерация токена на каждый `/auth/login` (session fixation структурно невозможна — `expires_at` уже фиксируется один раз при создании сессии, абсолютный 30-дневный TTL уже есть, не sliding). Работа — закрыть подтверждённые пробелы и осознанно перейти порог, который ADR-005 дважды откладывал с обоснованием «один provider не оправдывает схему»: schema-level `identities`-таблица (`backend/migrations/0020_identities.sql`: `employee_id, provider, provider_key, created_at, updated_at`, `UNIQUE(provider,provider_key)` + `UNIQUE(employee_id,provider)`) — единственный источник правды для auth-резолва (`auth/principal.ts::loadUser()`), не декоративная таблица поверх `employees.telegram_id`/`phone`/`password_hash`, которые остаются нетронутыми для не-auth потребителей (бот-уведомления по `telegram_id`, отображение в Команде и т.д.).

Разная семантика конфликта по provider, зафиксированная как инвариант владельцем продукта в процессе ревью: **Telegram** — ownership transfer (steal) разрешён и обязан сохранять уже протестированную продуктовую семантику self-bind (`data/repositories/identities.ts::transferIdentity()` — один атомарный `INSERT...ON CONFLICT (provider,provider_key) DO UPDATE SET employee_id=EXCLUDED.employee_id`, не `DELETE`+`INSERT` — race-safe при параллельных claim одного `provider_key`, Postgres сериализует через row-lock; `employees.ts::claimTelegramId()` — единственная точка изменения Telegram identity, employees-колонка и identities-строка обновляются внутри ОДНОЙ транзакции, никогда по отдельности).

**Phone** — ownership transfer НЕ разрешён автоматически (`bindIdentityStrict()` — тот же освобождающий `DELETE` для собственного переподвязывания, но БЕЗ `ON CONFLICT`: конфликт с чужим номером — сырой `23505` → `409 phone_taken`, уже обрабатываемый существующим кодом в `me/index.ts`/`session.ts`) — телефон credential boundary, не recovery-механизм, как Telegram self-bind. При разборе найден и исправлен реальный, **предшествующий 20.48.0** баг (не внесён этой правкой): `claimTelegramId()`'s `WITH cleared AS (UPDATE employees SET telegram_id=NULL WHERE telegram_id=$1)` CTE не имел data-зависимости с главным `UPDATE` — PostgreSQL не гарантирует порядок выполнения независимых data-modifying CTE в одном `WITH`-запросе, поэтому при переносе Telegram с УЖЕ занятой карточки на другую main-UPDATE мог проверить `UNIQUE(telegram_id)` РАНЬШЕ, чем `cleared` освобождал строку прежнего владельца, и словить ложный `23505`→`409` там, где ожидался успешный transfer; единственный существующий adversarial-тест (5 параллельных bind) не ловил это, потому что все 5 карточек стартовали НЕзанятыми (`cleared` матчил 0 строк вне зависимости от порядка) — сценарий «снять с уже занятой карточки» никогда не проверялся до нового transfer-теста в `me-bind.test.ts`.

Фикс — принудительная data-зависимость `WHERE id=$2 AND (SELECT count(*) FROM cleared) >= 0`, воспроизведён и подтверждён вручную (`node --input-type=module` против локального Postgres) до и после фикса. Session lifecycle: `softDeactivate()` (уже внутри `withTransaction`) теперь снимает `identities(provider='telegram')` (зеркалит `telegram_id=NULL`; phone НЕ трогается — переживает деактивацию, как и раньше `employees.phone`) и `DELETE FROM employee_sessions WHERE employee_id=$1` — деактивация инвалидирует browser-сессии немедленно, не полагаясь на то, что `requireActive` поймает это на следующем запросе; `/auth/reset/:token` тем же принципом отзывает ВСЕ существующие сессии сотрудника ДО выдачи новой (устройство A украдено → пароль меняют на B → токен на A не остаётся рабочим).

Новые `GET /auth/sessions` (список — только `id/created_at/last_seen_at/current`, без IP/User-Agent/геолокации, PII вне объёма), `DELETE /auth/sessions/:id` (ownership-scoped запросом; отзыв ТЕКУЩЕЙ сессии чистит оба cookie на ответе — API безопасен сам по себе, не полагается на то, что фронтенд не покажет кнопку на своей строке), `POST /auth/sessions/revoke-others` («выйти на всех других устройствах») — работают для ЛЮБОГО provider'а (Telegram-пользователь тоже видит и может отозвать свою browser-сессию, `current:false` на всех строках закономерно). CSRF — двухслойно: `Sec-Fetch-Site:cross-site` отклоняется сразу, до проверки токена; без этого заголовка (старые браузеры) `Origin` сверяется с уже существующим `MINI_APP_URL` (не изобретали параллельную env-переменную), не реконструируется из `Host`/`X-Forwarded-Host`; double-submit cookie `t2_csrf` (криптографически случайный, тот же генератор, что `sessionsRepo.generateToken()`, НЕ `httpOnly`, та же область видимости, что `t2_session`) ротируется вместе с ней на каждый логин. `auth/csrf.ts::requireCsrf` — глобальный `preHandler` сразу после `authPlugin`, срабатывает только при наличии cookie `t2_session` на мутирующем запросе (Telegram-путь не затронут вообще, без явного списка исключений по роутам) — `/auth/login`/`/auth/register`/`/auth/reset/:token` явно исключены отдельно (`EXEMPT_PATHS`): в браузере уже может лежать старая/подставная `t2_session` cookie (session fixation, протухшая сессия после рестарта БД), и без явного исключения честный вход падал бы в CSRF-отказ раньше, чем дошёл бы до собственной логики логина — найдено и исправлено собственным session-fixation-тестом до пуша. `POST /auth/logout` теперь чистит оба cookie, не только `t2_session`.

AAD (`{type,id,...}`, canonical-сериализация) криптографически связывает шифротекст с конкретной строкой — `id` резервируется явным `nextval()` до `INSERT` именно для этого; перенос шифротекст между записями ломает AEAD tag.
