## 20.20.0

**Recommend — подсказка «что сделать» в задаче из алерта, третий шаг Intelligence Layer.** Act уже существовал (18.4, создание задачи прямо из проблемы Command Center) — Recommend только подставляет ЧТО написать в задачу вместо пустого поля. Детерминированное правило cause→действие (`core/alerts/recommend.ts::suggestAction`), без LLM — та же дисциплина, что у Explain/Predict; менеджер всё равно видит подсказку в поле «Что сделать» перед созданием, редактирует или игнорирует, ничего не выполняется само. `understaffing` → «проверить график на ближайшие дни, рассмотреть усиление»; `shift_gap` → «связаться со сменой, уточнить причину»; `plan_miss_projected` → «скорректировать оставшуюся часть дня» с реальными числами прогноза/плана из payload. `network_wide` — сознательно БЕЗ совета: весь смысл этой причины «вероятно не локальная», предлагать точке действие было бы неверным сигналом; алерты до Explain/Predict (`low_mnp_ratio`/`no_sales_hour`/`cash_gap`) — тоже без подсказки, не выдумываем совет для типов вне подтверждённого скоупа.

Единственная точка подключения — `GET /command-center`, action `type=create_task`: `message` теперь `suggestAction(alert.alert_type, alert.payload) ?? alert.title` (прежнее поведение как фолбэк); `GET /alerts` (отдельная страница) не тронут — там пока нет кнопки создания задачи. 317 тестов (было 308) — 7 юнит-тестов на `suggestAction` (все причины + приоритет `understaffing` над `shift_gap` при обеих сразу + осознанное отсутствие совета у `network_wide`/старых типов) и 2 через реальный Postgres + HTTP

### Дополнение к описанию выпуска

Recommend — детерминированная подсказка «что сделать» (cause→действие, без LLM) предзаполняет создание задачи из алерта в Command Center

## 20.21.0

**Дилер — владелец сектора, новый уровень иерархии.** Не из конвейера Intelligence Layer — отдельный запрос по иерархии сети: над Сектором не было записи о том, кто им реально владеет. Новая цепочка: Дилер (ООО/ИП) → Сектор → Сеть (`organizations`) → Точка → Сотрудник. Только ownership-запись для отчётности/договоров — без своего входа, роли или дашборда, тем же лёгким приёмом, что уже был у самого сектора (заводится по имени из формы, не отдельный CRUD-экран). `dealers (id, name UNIQUE)` + `sectors.dealer_id` — один дилер может владеть несколькими секторами разом (FK не уникален), у сектора — ровно один дилер или ни одного.

Заводится в той же форме редактирования сети (`13-v14.js`), где уже было поле «Сектор» — новое поле «Дилер», upsert по имени (повторный ввод того же названия не плодит дубликат); привязывается к СЕКТОРУ этой сети, не к самой сети — если несколько сетей в одном секторе, у них общий дилер. Пустой ввод не трогает уже назначенного дилера — тот же приём, что у остальных опциональных полей этой формы (`chat_id` и т.п.), уже принятое ограничение, не новое. 322 теста (было 317) — 5 новых через реальный Postgres + HTTP; миграция 0015 и полный прогон дополнительно проверены на чистой БД с нуля, той же дисциплиной, что после 20.18.1

### Дополнение к описанию выпуска

Дилер — новый уровень иерархии над Сектором (ООО/ИП, владеет несколькими секторами), только ownership-запись без своего входа/роли

## 20.23.0

**Learn — сработала ли рекомендация, закрывает конвейер Intelligence Layer.** Explain → Predict → Recommend → Act уже были — Learn единственный шаг, отвечающий не "что произошло/предсказано/сделать", а "помогло ли на самом деле". Детерминированно, без LLM. Два независимых измерения: `plan_miss_projected` (Predict) — однодневное, реальный итог дня против `projectedTotal`, зафиксированного В МОМЕНТ алерта (тот самый пессимистичный read, что видел менеджер) → `recovered`/`still_missed`; `anomaly_vs_forecast` (Explain), только "тихие" дни (`payload.z < 0`) — рецидив: была ли у ТОЙ ЖЕ точки ещё одна просадка в следующие 7 дней → `recovered`/`recurred`, оцениваются только алерты старше окна.

Оба фиксируют `had_task` — была ли задача не просто создана, а ДОВЕДЕНА до конца (`status='done'`), отдельно отвечая на вопрос "помогает ли вообще Act", не только "стало ли лучше само по себе". Тот же дневной тик, что Explain (`core/alerts/service.ts`, hour===11), сразу после `checkAnomalyVsForecast()`. Новый `GET /alerts/effectiveness` (admin-only, как `/orgs`) — агрегированная сводка across org'ов; видна в «Отчётах» новой секцией "Эффективность рекомендаций" (admin-only). Пойман и исправлен реальный баг ещё до пуша: `payload`-независимый `id` из репозитория — bigint, pg возвращает строкой, а `Set` с id из отдельного запроса — числами; `had_task` всегда врал в `false` из-за `number !== string`, пока id не нормализован сразу после чтения — тот же класс бага, что уже ловили в `newbieCohorts` (19.x), там на датах.

Задним числом поймана и поправлена неточность в changelog 20.22.0 (см. выше). 328 тестов (было 322) — 6 новых через реальный Postgres, плюс 2 новых фронтенд-теста (`frontend/tests`, 60 → 62)

## 20.38.0

**Десктоп-раскладка — один брейкпоинт правит всё приложение разом.** Вход без Telegram (20.37.0) открыл сайт для настоящего браузера, но вся вёрстка написана mobile-first под Telegram Mini App и ни разу не адаптирована под широкий экран — во всём `styles.css` (2091 строка) существовал ровно один `@media` (`prefers-reduced-motion`), никаких брейкпоинтов по ширине; `.sheet` не имел `max-width` вообще — на мониторе растягивался на всю ширину. Не редизайн под "десктоп-плотность" (переосмысление контента каждого экрана по отдельности — другой масштаб работы), а тот же приём, что Telegram Web/WhatsApp Web/Twitter: то же мобильное приложение как единая раскладка, но центрированная колонка-панель (800px) на широком экране вместо растянутой на весь монитор.

CSS не бандлится Vite и не разбит по страницам — один блок в конце `styles.css` правит всё приложение разом, ни одной страницы отдельно трогать не пришлось. `@media (min-width: 860px)` — единственный брейкпоинт, ниже не меняется ни пиксель, реальный Telegram Mini App (всегда уже порога) ничем не рискует. `.app-header`/`.sheet`/`.bottom-nav` получают `max-width:800px`, `.sheet` округляет все четыре угла и получает тень ("плавающая панель" на нейтральном фоне `body` вместо страницы во всю ширину), `.fab` пересчитывает `right` через `calc(50vw - 400px + …)` — от края фрейма, не от физического края окна. `.lk-actions-grid` ("Мой план", 8 кнопок) — с жёстких 2 колонок на 4. `.sum-sch-table` (сводный график, до 31 дня) честно не перестаёт скроллиться горизонтально даже на 800px — реальная широкая таблица, не искусственное ограничение; шрифт 11px→12px и колонка с именем 140px→160px читаемее, `overflow-x:auto` остаётся, нормальный паттерн и для настоящих десктопных таблиц с диапазоном дат.

Модалка (`.overlay`/`.sheet-modal`) — на десктопе bottom-sheet не единственно верный паттерн, чисто мобильная условность; на 860px+ обычный центрированный диалог с фейдом. Логин-экран (`.gate-shell`, уже `max-width:420px` с 20.37.0) переделки не потребовал — пустое пространство вокруг получило мягкий radial-gradient фон теми же токенами, что уже использует `.gate-card .bind-glow` внутри карточки. Отдельный блок `@media (min-width:860px) and (hover:hover)` — не просто по ширине, `(hover:hover)` исключает touch-ноутбуки/планшеты в альбомной ориентации, которым залипающий hover только мешает; во всём файле раньше не было ни одного `:hover`, только `:active` (тактильная обратная связь для тача) — добавлены `.row`/`.nav-item`/`.lk-action`/`.fab`.

Найдена и обойдена реальная specificity-ловушка: `showAccessGate()`/`showLoginGate()` при каждом показе выставляют `background` инлайн через `gate.style.cssText` — обычный CSS-класс/id это не перебивает, фон логин-экрана на десктопе пришлось поставить через `!important` с явным комментарием почему, а не правкой JS (план был "ровно один файл `styles.css`"). Верификация: чисто CSS, без единой строчки JS — `tsc`/vitest не покрывают визуальный результат (jsdom не считает layout/paint), автоматических тестов на это писать нечего; `npm run smoke:frontend` прогнан, живой сервер подтвердил, что новый блок реально попал в файл, отданный по HTTP.

Честно: правки НЕ проверены визуально реальным браузером/скриншотом — инструмент недоступен в текущем окружении, то же ограничение, что уже отмечалось при миграции `reports.js` в 20.12.0

## 20.39.1

**Хотфикс по подробному ревью владельца продукта сразу после 20.39.0.** Реальная находка — тот же класс бага, что `.bottom-nav`, во второй раз: `resize`-обработчик `initSwipePanels()` (`nav.ts`) на каждый resize вызывал `settle(current, false)`, которая безусловно выставляет `track.style.height` под высоту ТОЛЬКО текущей панели (нужно на mobile — «Мой день»/«Сеть сегодня» разной высоты по дням) — на desktop, где обе панели видны одновременно как grid, тот же inline `height` от последнего мобильного состояния мог обрезать более высокую вторую колонку при переходе mobile→desktop без перезагрузки страницы (реальный сценарий — ресайз окна через границу 860px).

Резолвер теперь на `window.innerWidth>=860` сбрасывает `track.style.height`/`transform` в `''` вместо вызова `settle()` — воспроизведено и проверено живьём (Playwright): inline `height:122px`/`transform` от мобильного состояния после ресайза до 1200px корректно очищаются, computed `display:grid` подтверждён. Убран дублирующий `.sidebar .nav-item:hover` (полностью покрывался уже существующим `.nav-item:hover`, cosmetic). Активный пункт сайдбара получил тонкий индикатор слева (`::before`, `var(--primary)`) поверх уже существующей заливки `.primary-soft`.
