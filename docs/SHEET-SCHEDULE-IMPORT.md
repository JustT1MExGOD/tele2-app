# Google Таблицы ↔ график: двусторонняя синхронизация

[Документация](README.md) · [Обзор проекта](../README.md)

Правка ячейки в Google Таблице сразу применяется в графике приложения, и
наоборот — правка в приложении сразу уходит в таблицу. Обе стороны
равноправны: побеждает тот, кто правил последним, в любую сторону.

## Принцип: последний правил — тот и победил

Каждая строка графика (`schedules`) несёт `source: 'manual' | 'sheet_import'` —
но это больше не защита одной стороны от другой (так было на первой,
однонаправленной версии этой фичи), а только учёт, кто трогал строку
последним:

- Правка через приложение (`POST /schedules`, `/schedules/bulk`, admin-
  коррекции, привязка «Замены» к реальной точке при `/shifts/open`) ставит
  `source='manual'` и **толкает** изменение в таблицу
  (`core/integrations/sheet-schedule-export.ts`).
- Правка через таблицу (`upsertFromSheet`/`deleteOneFromSheet` в
  `backend/src/data/repositories/schedules.ts`) применяется **безусловно** —
  перезаписывает строку независимо от текущего `source` — и ставит
  `source='sheet_import'`.

Почему это не зацикливается: только «app-side» писатели толкают
изменение обратно в таблицу; `upsertFromSheet`/`deleteOneFromSheet` (сам
приём правки ИЗ таблицы) — никогда. Правка из таблицы просто применяется
и на этом останавливается; она не порождает эхо обратно в ту же таблицу.

## Сопоставление сотрудника

Таблица знает сотрудника только по написанному имени (`ФИО`). Сопоставление
с `employees.id` (`backend/src/core/integrations/sheet-name-match.ts`,
используется в обе стороны — и импортом, и экспортом):

1. Уже подтверждённое соответствие (`sheet_schedule_mappings`) — применяется сразу.
2. Точное совпадение имени (без учёта регистра/пробелов/ё-е) — подтверждается
   автоматически, дальше ведёт себя как п.1.
3. Похожее, но не точное имя (опечатка) — строка уходит в очередь
   **Admin Center → «Импорт графика из Таблиц»** и ничего не пишет в
   график, пока админ не подтвердит, кто это. (Это правило только для
   направления «таблица → приложение» — направление «приложение → таблица»
   при отсутствии совпадения просто добавляет нового сотрудника новым
   блоком строк в конец листа, см. ниже.)
4. Совсем не похоже ни на кого (таблица → приложение) — тоже в очередь, без предложенного кандидата.

## Формат ячейки

| Значение | Смысл |
| --- | --- |
| `10-22`, `9-21` | смена с такими часами (конец раньше начала = смена через полночь) |
| `вых`, `выходной`, `отп`, `отпуск`, пусто | выходной — удаляет смену на этот день |
| что угодно другое | не разобрано, строка пропускается |

Часы **всегда** пересчитываются из времени смены (`10-22` → 12ч) в обе
стороны — направление «приложение → таблица» тоже пишет посчитанные
часы, а не какое-то отдельное значение. Правка второй (часовой) строки
пары сотрудника в самой таблице сама по себе безвредна — её значение
(голое число) не проходит формат `HH-HH`/выходного и тихо пропускается.

## Точки продаж — по цвету ячейки

Одна таблица покрывает несколько точек сразу — какая именно, определяется
**цветом заливки** ячейки (не текстом, не отдельной колонкой). Цвета этой
конкретной таблицы:

| Цвет | Точка | `store_id` |
| --- | --- | --- |
| `#ff6d01` (оранжевый) | Калинина 2 | `kalinina2` |
| `#ffd966` (жёлтый) | Калинина 11 | `kalinina11` |
| `#6d9eeb` (голубой) | Космонавтов 20а | `kosmonavtov` |
| `#00ff00` (зелёный) | Замена (без точки) | `__REPLACEMENT__` |

`'__REPLACEMENT__'` — то же самое значение, что и
`REPLACEMENT_PLACEHOLDER_STORE_ID` (`backend/src/shared/replacement.ts`),
которым пользуется сама форма графика в приложении для «Замены» (когда
известно, что сотрудник работает подмену, но не в какой конкретно точке).

Если добавится ещё одна точка/цвет — новую пару нужно добавить **в двух
местах**: в `COLOR_TO_STORE` константе Apps Script (направление таблица →
приложение) и в `STORE_TO_COLOR` в
`backend/src/core/integrations/sheet-schedule-export.ts` (обратное
направление) — держать в синхроне вручную, единого источника правды для
этой карты пока нет.

## Направление «таблица → приложение»: настройка

Секрет на сервере (Railway):

```
SHEETS_WEBHOOK_SECRET=<длинная случайная строка>
```

Без него `POST /integrations/sheets/schedule-webhook` отвечает `503` —
это направление не активно, пока секрет не задан.

В Google Таблице: **Расширения → Apps Script**, вставить и настроить
константы вверху (`WEBHOOK_URL`, `WEBHOOK_SECRET`, `ORG_ID`, `COLOR_TO_STORE`):

Реальная раскладка **этой** таблицы (обнаружена живой отладкой, не
угадана заранее — если раскладка когда-нибудь изменится, эти четыре
константы и придётся поправить):
- строка 8 — настоящие даты (значения типа `Date`, не текст) — не строка 1;
- строка 9 — сокращения дней недели (декоративные, скрипт их не читает);
- строка 10 — первый сотрудник;
- колонка A — ФИО, смёрджена на пару строк одного сотрудника;
- колонки B/C — служебные подписи («2\2» / «режим» / «рабочие часы»), не даты;
- колонка D — первая колонка с датами.

```javascript
const WEBHOOK_URL = 'https://<ваш-сервер>/integrations/sheets/schedule-webhook';
const WEBHOOK_SECRET = '<тот же SHEETS_WEBHOOK_SECRET, что на сервере>';
const ORG_ID = 'default';
const NAME_COLUMN = 1;        // колонка A — ФИО (смёрджена на пару строк сотрудника)
const HEADER_ROW = 8;         // строка с настоящими датами (значения типа Date)
const FIRST_DATA_ROW = 10;    // первая строка с данными сотрудников
const FIRST_DATE_COLUMN = 4;  // колонка D — B/C служебные (режим/часы), не даты

const COLOR_TO_STORE = {
  '#ff6d01': 'kalinina2',
  '#ffd966': 'kalinina11',
  '#6d9eeb': 'kosmonavtov',
  '#00ff00': '__REPLACEMENT__'   // замена
};

function getEmployeeName_(sheet, row) {
  const cell = sheet.getRange(row, NAME_COLUMN);
  const merged = cell.getMergedRanges();
  const anchor = merged.length ? merged[0].getCell(1, 1) : cell;
  return anchor.getValue().toString().trim();
}

function onEdit(e) {
  const sheet = e.range.getSheet();
  const row = e.range.getRow();
  const col = e.range.getColumn();
  if (row < FIRST_DATA_ROW || col < FIRST_DATE_COLUMN) return;

  const dateVal = sheet.getRange(HEADER_ROW, col).getValue();
  if (!(dateVal instanceof Date)) return; // над этой колонкой нет даты — не трогаем

  const workDate = Utilities.formatDate(dateVal, sheet.getParent().getSpreadsheetTimeZone(), 'yyyy-MM-dd');
  const employeeName = getEmployeeName_(sheet, row);
  if (!employeeName) return;

  const shiftRaw = e.range.getValue().toString().trim();
  const storeId = COLOR_TO_STORE[e.range.getBackground()] || '';

  const payload = {
    org_id: ORG_ID,
    store_id: storeId,
    employee_name: employeeName,
    work_date: workDate,
    shift_raw: shiftRaw
  };

  UrlFetchApp.fetch(WEBHOOK_URL, {
    method: 'post',
    contentType: 'application/json',
    headers: { 'X-Sheets-Webhook-Secret': WEBHOOK_SECRET },
    payload: JSON.stringify(payload),
    muteHttpExceptions: true
  });
}
```

`onEdit` как простой (не установленный) триггер **не может** делать
внешние вызовы (`UrlFetchApp.fetch`) на некоторых аккаунтах — Google
режет права простых триггеров. Подтверждено живой отладкой: ошибка в
этом случае выглядит как `Exception: Указанных разрешений недостаточно
для звонка пользователю UrlFetchApp.fetch. Требуемые разрешения:
https://www.googleapis.com/auth/script.external_request`. Если она
появилась — замените простой триггер на установленный:
**Триггеры (значок часов слева) → Добавить триггер → функция `onEdit` →
источник события «Из таблицы» → тип события «При редактировании» →
Сохранить**, затем один раз пройти экран согласия Google (это нормально
для собственного неопубликованного скрипта — не настоящее
предупреждение безопасности): выбрать аккаунт → «Google не проверил это
приложение» → **Дополнительные настройки** → **Перейти к [название
проекта] (небезопасно)** → **Разрешить**.

## Направление «приложение → таблица»: настройка

Отдельный, новый сервис-аккаунт Google Cloud (не тот же секрет, что
выше — это авторизация сервер→Sheets API, а не таблица→сервер):

1. [Google Cloud Console](https://console.cloud.google.com/) → проект →
   включить **Google Sheets API**.
2. IAM & Admin → Service Accounts → создать → сгенерировать JSON-ключ (скачать).
3. Открыть саму Google Таблицу → **Настройки доступа** → добавить
   `client_email` сервис-аккаунта (вида
   `...@...iam.gserviceaccount.com`) с правами **Редактор**.
4. На сервере (Railway) задать:
   ```
   GOOGLE_SHEETS_SA_KEY_BASE64=<весь скачанный JSON-ключ, целиком, в base64>
   GOOGLE_SHEETS_SPREADSHEET_ID=<id таблицы из её URL>
   ```
   Без обеих переменных `pushScheduleChangeToSheet` — тихий no-op: фича
   не активна, ничего не ломает и ничего не отправляет.

Дальше всё автоматически: `core/integrations/sheet-schedule-export.ts`
находит лист месяца по дате (`"Ноябрь 2026"` и т.п.), ищет колонку по
той же строке-шапке с датами (строка 8), ищет строку сотрудника по
`sheet_schedule_mappings` (если уже подтверждён импортом) или живым
сопоставлением имени по колонке A; если сотрудника в листе вообще ещё
нет — добавляет новый блок из двух строк в конец листа (ФИО в
смёрдженной ячейке A, служебные подписи `"2\2"`/`"режим"`/`"рабочие
часы"` по образцу уже существующих строк — это грубое приближение форматирования, не точная копия). Пишет текст смены, часы и цвет
(обратная карта `STORE_TO_COLOR`, см. выше).

## Разовый перенос истории (backfill)

Копирует всё, что уже есть в `schedules`, в таблицу — разово, вручную,
после того как сервис-аккаунт настроен и один живой пуш (см. «Проверка»)
подтвердил, что всё работает:

```bash
cd backend
npx tsx scripts/sheet-export-backfill.ts 2026-09-01   # дата — с какого work_date начать, по умолчанию 2026-09-01
```

Идёт по одной строке за раз (не пачками) с небольшой паузой между
вызовами, чтобы не упереться в квоту записи Sheets API — для нескольких
месяцев истории это может занять несколько минут, это ожидаемо.

## Проверка

1. Впишите в таблице смену новому/тестовому сотруднику, чьего имени точно
   нет в системе — она должна появиться в Admin Center → «Импорт графика
   из Таблиц» как ожидающая подтверждения.
2. Впишите смену сотруднику, чьё ФИО в таблице совпадает с `employees.full_name`
   один-в-один — она должна сразу появиться в графике приложения.
3. Поправьте расписание в приложении для известного сотрудника/даты —
   через несколько секунд ячейка в таблице (текст, часы, цвет) должна
   обновиться сама.
4. Измените ту же ячейку в таблице ещё раз — она должна применяться в
   приложении, даже если до этого её правили в приложении (симметрия,
   не «приложение всегда побеждает»).
5. Поправьте расписание в приложении ещё раз для той же ячейки — таблица
   должна снова перевернуться на сторону приложения. Если шаги 3-5 все
   отработали — направление действительно двустороннее, а не
   однонаправленный пуш, притворяющийся симметричным.

## Известные ограничения

- Точка определяется по **точному** совпадению hex-кода фона ячейки — цвет,
  которого нет в карте (`COLOR_TO_STORE`/`STORE_TO_COLOR`), тихо
  пропускается, ничего не сломав, но и ничего не применив.
- Новый лист на новый месяц **не создаётся автоматически** ни в одну
  сторону — ни импортом (лист должен уже существовать под правильным
  именем «Месяц Год»), ни экспортом (`pushScheduleChangeToSheet` просто
  пропускает пуш с предупреждением в лог, если листа для этого месяца
  ещё нет). Добавление нового **сотрудника** в существующий лист —
  поддерживается (направление приложение → таблица), добавление нового
  **месяца** — нет.
- Не всякая правка внутри приложения толкается в таблицу — только
  ежедневное редактирование графика (`POST/DELETE /schedules`,
  `/schedules/bulk`, admin-коррекции графика, привязка «Замены» к
  реальной точке). Три более редких, объёмных пути **намеренно не
  толкают** изменения в таблицу (иначе пришлось бы делать сотни
  несгруппированных вызовов Sheets API за один запрос и почти
  гарантированно упереться в квоту): массовая генерация/применение
  графика на месяц (schedule-generator APPLY,
  `core/schedules/application/apply-draft.ts`), очистка будущих смен
  при деактивации/переносе сотрудника
  (`deleteFutureForEmployee`, `api/routes/org/employees.ts`), и Admin
  Center → «Очистить график точки за месяц»
  (`core/admin/schedule-correction.ts::clearStoreMonth`). После любого
  из этих трёх действий таблицу нужно досогласовать вручную или
  повторным запуском backfill-скрипта на нужный диапазон дат.
- Нет очереди повторных попыток на случай сбоя пуша — если Google API
  временно недоступен или упала конкретная запись, пуш просто
  логируется как ошибка и не повторяется сам; данные в Postgres при
  этом корректны всегда, рассинхрон только в самой таблице до следующей
  правки этой же ячейки (в любую сторону) или повторного backfill.
- Нет автотеста, поднимающего реальный Postgres+живой Google Sheets API
  одновременно — DB-часть (симметрия `source`, очередь подтверждения)
  покрыта тестами на реальном одноразовом Postgres
  (`backend/tests/isolation/sheet-schedule-import-priority.test.ts`,
  `sheet-import-webhook.test.ts`), чистые функции обоих направлений —
  unit-тестами (`sheet-schedule-import.test.ts`,
  `sheet-schedule-export.test.ts`); сам живой Sheets API вызов проверен
  только вручную (см. «Проверка» выше).
