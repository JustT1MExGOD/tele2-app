# Аудит клиентов: дизайн, UX, нативность и визуал

[Документация](README.md) · [Обзор проекта](../README.md)

Актуальный baseline-аудит трёх клиентских поверхностей T2 Sales: веб-клиента,
который используется в браузере, Telegram Mini App и Capacitor Android, нативного
Compose Desktop для Windows и нативного Compose Android. Документ фиксирует
состояние исходников на **29 октября 2026 года** и служит входом в поэтапную
полировку интерфейсов.

Аудит выполнен по четырём осям:

- **Дизайн** — единообразие токенов, типографики, цветов, отступов и компонентов.
- **UX** — навигация, понятность действий, состояния загрузки/ошибки/пустого результата,
  обратная связь и достижимость функций.
- **Нативность** — соответствие платформе: окно и клавиатура Windows, жесты и
  системная навигация Android, safe area, back, insets, touch targets.
- **Визуал** — иерархия, плотность, выравнивание, читабельность, иконки и общий
  уровень полировки.

Это не визуальная приёмка каждого экрана по скриншотам: подключённого Android-
устройства в момент аудита не было, а живой Desktop-билд требовал отдельной
пересборки. Такие проверки обозначены как **«не проверялось»**; выводы ниже
подтверждены чтением исходников.

## Итоговые оценки

Оценка — не маркетинговая метка и не оценка бизнес-функциональности. Это
приоритетная оценка текущей пользовательской поверхности по четырём осям.

| Клиент | Оценка | Что уже хорошо | Главный долг |
| --- | --- | --- | --- |
| Веб / Telegram Mini App / Capacitor | B | зрелые CSS-токены, safe area Telegram/iOS, три responsive-уровня, много пустых состояний | сетевые ошибки часто заканчиваются статичным сообщением без «Повторить»; часть страниц всё ещё смешивает токены и inline-стили |
| Compose Desktop | A− | настоящий Windows-клиент: трей, глобальные хоткеи, command palette, сохранение окна, системная тема, outbox | не все длинные списки имеют видимый scrollbar; несколько admin-экранов теряют ошибку загрузки в пустое состояние |
| Compose Android | B+ | `BackHandler`, системные insets, keyboard-aware bottom nav, bottom sheets, touch-анимации, общие токены | часть портированных экранов остаётся desktop-first; retry и адаптация широких данных закрыты не везде |

Оценка может измениться после живой проверки на реальном телефоне и Windows-окне.
Кодовая проверка уже проведена; визуальная проверка на устройствах — отдельный
этап, см. [критерии готовности](#критерии-готовности).

## Общие сильные стороны

### Один визуальный язык

Нативные клиенты используют `native/shared/.../theme/T2Tokens.kt`, где цвета,
радиусы, отступы и размеры шрифта перенесены из `backend/frontend/styles.css`
(`:root`, строки 57–181). Это хороший принцип: клиентские реализации отличаются
нативными компонентами, но не случайной палитрой.

### Продуманная работа с окружением

Веб-клиент учитывает `env(safe-area-inset-*)`, Telegram
`contentSafeAreaInset`, `100dvh` и запрет конфликтующего pull-to-refresh.
Android-клиент использует `statusBarsPadding`, `navigationBarsPadding` и
`imePadding`; нижняя навигация скрывается, когда открыта клавиатура.

### Нативный Desktop не является растянутым мобильным экраном

`native/desktopApp/.../Main.kt` и `ui/shell/AppShell.kt` реализуют поведение,
которого ожидаешь от Windows-приложения:

- системный трей и меню приложения;
- запуск вместе с Windows и режим «закрыть в трей»;
- глобальный hotkey для быстрой продажи;
- `Ctrl+K` для command palette и `Ctrl+N` для новой продажи;
- single-instance;
- сохранение размера, положения и состояния maximize;
- следование системной светлой/тёмной теме.

### Ошибки уже имеют общую нативную основу

`ErrorState(text, onRetry)` уже существует в:

- `native/desktopApp/.../ui/components/Layout.kt`;
- `native/androidApp/.../ui/Compat.kt`.

Следовательно, основная работа — не изобретение компонента, а доведение всех
экранов до единого контракта и добавление аналогичного безопасного helper-а в
веб-клиент.

## Веб-клиент, Telegram Mini App и Capacitor Android

### Дизайн

Сильная сторона — полноценная система токенов в
`backend/frontend/styles.css`:

- отдельные light/dark surfaces;
- semantic tokens для success/danger/warning;
- шкалы радиусов, отступов, типографики и motion;
- отдельные токены для Telegram/iOS safe area;
- комментарии с обоснованием контраста WCAG для `--hint` и
  `--primary-text-bg`.

Responsive-стратегия разделена на три уровня:

- `<860px` — мобильная поверхность;
- `≥860px` — sidebar/topbar desktop shell;
- `≥1200px` и `≥1600px` — расширенная раскладка главной.

Риск — часть страниц всё ещё использует большое количество inline-стилей и
локальных числовых значений: в `backend/frontend/src/pages/` обнаружено много
динамической HTML-генерации и inline CSS. Для динамических цветов, размеров
графика и safe-area это оправдано; для обычных карточек, отступов и кнопок это
постепенно размывает дизайн-систему.

### UX

Пустые результаты в целом описаны хорошо: вместо пустого белого места чаще
показывается объяснение (`нет задач`, `очередь пуста`, `нет сотрудников`). Но
ошибка загрузки часто превращается в тупик:

- `pages/schedule/index.ts` выводит `Ошибка загрузки`/`Ошибка загрузки графика`;
- `pages/team/index.ts` — `Не получилось загрузить команду`;
- `pages/alerts/index.ts` — `Не удалось загрузить алерты`;
- `pages/tasks/index.ts` — `Не удалось загрузить задачи`;
- `pages/command-center/index.ts` — сообщение о недоступности Command Center;
- `pages/employee-profile/index.ts`, `dealers/index.ts`, `leaderboard/index.ts` и
  другие страницы имеют аналогичные статичные `empty`-сообщения.

Пользователь не получает повторное действие и вынужден обновлять страницу или
уходить на другой экран. Это первый приоритет текущего спринта.

Дополнительные наблюдения:

- страница `today` остаётся зарегистрированной в старом диспетчере, но из UI не
  достижима — кандидат на удаление после отдельной проверки legacy-маршрутов;
- пользовательской сортировки/фильтрации в большинстве списков нет: сортировка
  обычно фиксирована в коде;
- retry для сообщений чата и offline-очереди уже есть, но это предметные retry,
  их нельзя использовать как общий page-load helper.

### Нативность и визуал

Telegram-специфика обработана тщательно: init data берётся независимо от скорости
загрузки Telegram SDK, safe-area не складывается дважды, а экран не должен
преждевременно падать в phone/password flow при медленном SDK.

Визуально основа стабильная, однако HTML-строки разных эпох соседствуют:
часть страниц использует общие `.section`, `.row`, `.btn-main` и токены, а часть
задаёт размеры и цвета inline. После retry-спринта нужен отдельный проход по
наиболее посещаемым страницам: Home, Plan, Schedule, Team, Admin Center.

## Нативный Windows Desktop

### Дизайн и визуал

`AppShell` использует sidebar, header с avatar/breadcrumb, status-пилюли точки и
даты, network/outbox индикаторы, ограниченную ширину рабочей области и общую
тёмную/светлую тему. Это правильная иерархия для большой ширины, а не копия
нижней мобильной навигации.

### UX и нативность

Сильные Windows-паттерны перечислены выше. При этом основной shell использует
общий вертикальный `Column(...verticalScroll(...))`, а видимый
`VerticalScrollbar` найден только в отдельных широких сценариях, прежде всего
в графике. На длинных списках пользователю не всегда очевидно, что ниже есть
ещё данные, и отсутствует возможность схватить ползунок мышью.

Реальный UX-дефект — ошибки загрузки, которые превращаются в пустые списки:

- `ui/admincenter/AcMiranda.kt` делает несколько запросов и при каждом failure
  записывает `emptyList()`, поэтому «нет данных» неотличимо от «сервер упал»;
- `ui/admincenter/AcSales.kt` показывает `EmptyText("Не удалось загрузить строку")`
  без retry для выбранной строки;
- ряд экранов показывает `ErrorState`, но не передаёт `onRetry`.

### Приоритеты Desktop

1. Не смешивать failure с empty state в Miranda; добавить независимые флаги ошибок
   и retry для каждого блока или общий retry всех четырёх запросов.
2. Добавить retry для detail-загрузки продажи.
3. Провести проход по экранам, где `ErrorState` уже есть, но callback отсутствует.
4. Добавить видимый scrollbar на длинные desktop-списки, не превращая каждый
   короткий экран в отдельный scroll-контейнер.

## Нативный Android

### Дизайн и нативность

Android-клиент использует отдельную мобильную оболочку, а не desktop sidebar:

- шесть нижних вкладок с векторными иконками;
- стек `Page` поверх вкладок;
- `BackHandler` закрывает открытую страницу;
- `PageScaffold` учитывает status bar;
- bottom sheets закрываются свайпом вниз;
- bottom nav скрывается при IME/клавиатуре;
- touch feedback и небольшие переходы присутствуют в основных действиях.

Это соответствует Android-модели лучше, чем буквальная web-wrapper реализация.

### UX-долг портированных экранов

Портирование из Desktop ускорило parity, но некоторые экраны остаются desktop-first:

- `Compat.kt::WideTable` намеренно задаёт минимальную ширину и включает
  горизонтальный scroll;
- `AuditScreen` и `OrgsScreen` используют этот компонент. Для действительно
  широких данных это допустимо, но на телефоне карточная раскладка или выбор
  колонок была бы удобнее;
- длинные списки в основном используют обычные `Column`/scroll, а не
  `LazyColumn`; видимых scrollbar-индикаторов нет.

Главный конкретный дефект — неполный retry:

| Экран | Проблема |
| --- | --- |
| `AcMiranda` | несколько запросов silently превращают failure в пустой список |
| `AcSales` | detail failure без retry |
| `Forecast` | ошибка прогноза без retry |
| `PlanDrafts` | ошибки чтения/расчёта сообщаются без повторения загрузки |
| `ReportImg` | ошибка генерации/рендера без общего retry |
| `Reports` | ошибка загрузки части данных без retry |
| `Support` | ошибка FAQ без retry |
| `Tasks` | ошибка списка/детали без retry |

На части остальных экранов `ErrorState` уже подключён, но callback всё ещё не
передан (`Announce`, `Audit`, `Cash`, `CommandCenter`, `Heatmap`, `Live`,
`MonthPlan`, `Orgs`, `StoreProfile` и другие). Это будет закрываться тем же
проходом, с сохранением локального `reload`-счётчика.

### Порядок текущего спринта

1. ✅ Веб: добавлен `backend/frontend/src/shared/load-error.ts` — безопасный
   `renderLoadError(container, message, retry)` без inline `onclick`, с
   disabled-состоянием кнопки на время повтора и `role="alert"`. Подключён к
   `alerts`, `tasks`, `command-center`, `home` (в т.ч. detail-ошибкам через
   модалку). tsc и `smoke:frontend` чистые.
2. ✅ Native: `ErrorState(..., onRetry = { reload++ })` проведён по всем
   экранам, где `reload`-счётчик уже существовал или мог быть добавлен без
   переделки. На Desktop закрыто ~20 экранов (AcCorrections, AcTabsB ×4,
   AdminCenterScreen stores+audit, AcSales detail, AlertsScreen,
   AnnounceScreen, BfqScreen, CashScreen, CommandCenter, HistoryScreen,
   LeaderboardScreen, MonthPlanScreen, NetMonthScreen, PlanDayScreen,
   StoreProfileScreen, LiveScreen). На Android — аналогично для тех же
   экранов в `ported/` и `PlanDayScreen` (через `AppState.refreshTick`).
   Heatmap намеренно оставлен без `onRetry`: экран живёт в poll-цикле с
   `delay(REFRESH_MS)` и сам перезапрашивает данные — сообщение ошибки
   изменено на «обновится автоматически», чтобы не обещать ручное действие.
3. ✅ Native Miranda: `AcMiranda` больше не маскирует сетевые ошибки в пустые
   списки — каждый из четырёх независимых запросов (pending devices, corporate
   accounts, available accounts, contact groups) имеет свой `*Failed`-флаг и
   показывает `ErrorState` с `onRetry = { reload++ }` вместо `emptyList()`.
4. ✅ Web-охват `renderLoadError` доведён до конца: `employee-profile`,
   `dealers`, `leaderboard`, `network-admin` (forecast/announcements/orgs/
   audit), `plans-bfq` (BFQ/month/net), `team`, `schedule` (plan-day, today,
   month, staffing-editor), `support` (FAQ, tickets), `store-profile`,
   `access-supervisor`, `cash-metrics`, все вкладки `admin-center` (audit,
   business-rules, feature-flags, operations, org-settings, overview,
   sheet-import, stores list+detail, employees detail, plan/sale/schedule/
   shift-correction detail, miranda-devices all four loaders). User-action
   errors (поиск, предпросмотр) намеренно оставлены как «Ошибка поиска» —
   это не screen-level загрузка.
5. Запланировано: мёртвый маршрут `today`, Desktop scrollbars, Android
   адаптивные карточки для широких таблиц, живой скриншот-аудит.

## Критерии готовности

### Для retry

- при временном отказе API пользователь видит понятное сообщение;
- есть кнопка `Повторить` с touch target не меньше обычной кнопки;
- повтор не сбрасывает текущий фильтр, выбранный месяц, выбранный объект или
  открытый detail;
- повтор не создаёт дублирующих запросов и не вызывает мутацию;
- empty result и network failure визуально различаются;
- после успешного повторения ошибка исчезает и данные показываются без ручной
  перезагрузки приложения.

### Для нативной полировки

- Desktop: окно можно изменить, свернуть в трей, использовать мышью и клавиатурой;
- Android: системный Back закрывает вложенный экран/лист, клавиатура не закрывает
  важные кнопки, safe area не перекрывает контент;
- обе платформы: текст не обрезается на узкой ширине, кнопки имеют понятный
  pressed/hover state, ошибки и пустые состояния имеют одинаковую иерархию.

### Для визуальной приёмки

- Desktop-билд запускается без старых зависших JVM-окон;
- на Android проверяются реальные телефонные размеры и системная тема;
- для Home, Schedule, Team, Admin Center, Chat и Profile сохраняются скриншоты
  light/dark или явно фиксируется, что проверка не проводилась;
- результаты живой проверки добавляются в этот документ с датой и версией.
