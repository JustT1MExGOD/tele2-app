# Runbook

> Операционные процедуры для прод-инцидентов — не «как это работает»
> ([ARCHITECTURE.md](./ARCHITECTURE.md), [SECURITY.md](./SECURITY.md)), а
> «что конкретно сделать руками прямо сейчас». Каждая процедура здесь —
> основана на реальном механизме в коде, не на общих best practices.

## Восстановление доступа (admin)

Если единственный admin потерял доступ (роль случайно понижена, аккаунт
деактивирован) — восстановление через прямой SQL, **не рутинная
операция**, только для реального инцидента:

```sql
UPDATE employees
SET access_status = 'active', is_active = true, role = 'admin'
WHERE telegram_id = <TG_ID>;
```

Через Railway → Postgres → Query (или `psql` с `DATABASE_URL` из
переменных сервиса). По правилам этого репозитория (`CLAUDE.md`) — прямая
запись в прод-БД в обход миграций требует явного подтверждения владельца
продукта, это не входит в предодобренный автономный набор действий.

## Ротация `BOT_TOKEN`

Компрометация токена (утёк в лог, коммит, скриншот) — токен даёт полный
контроль над ботом (отправка сообщений от его имени, чтение всех
входящих). Полноценного лога вызовов Bot API на нашей стороне нет —
Telegram не отдаёт историю запросов задним числом; то, что видно нам —
только собственный `audit_log` (действия пользователей в самом
приложении, не вызовы Bot API снаружи).

1. В [@BotFather](https://t.me/BotFather) → `/mybots` → выбрать бота →
   **API Token** → **Revoke current token**. Старый токен перестаёт
   приниматься Telegram немедленно — активная `long polling`-сессия с ним
   начнёт получать `401 Unauthorized` от Telegram API.
2. Скопировать новый токен, обновить переменную `BOT_TOKEN` в Railway
   (Variables сервиса) — сохранение переменной сама по себе передеплоя не
   требует, но новый процесс должен запуститься с ней в окружении
   (Railway обычно рестартует сервис на изменение переменных автоматически;
   если нет — форсировать redeploy вручную).
3. Убедиться, что **Replicas = 1** (см. [DEVELOPMENT.md](./DEVELOPMENT.md))
   — второй одновременный `polling` на новом токене даст тот же
   `409 getUpdates`, что и раньше.
4. Проверить `railway logs` на `🤖 Bot polling started` без ошибок сразу
   после рестарта.
5. Если есть подозрение, что токеном реально воспользовались — единственный
   доступный нам след: свериться с `audit_log` за окно компрометации на
   аномальные действия (роли, доступы) от лица настоящих пользователей —
   сам факт отправки сообщений извне через Bot API в нём не отражается,
   это ограничение Telegram, не пробел в логировании приложения.

## Миграции только вперёд, без отката

В проекте нет команды `migrate down` и никогда не было (`src/data/db/migrate.ts`
— только применение файлов по порядку, без down-скриптов). Если задеплоена
миграция, ломающая схему или данные:

1. **Не редактировать** уже применённый файл в `backend/migrations/` —
   `schema_migrations` уже пометила его применённым, повторно он не
   выполнится, а на новых окружениях (CI, чужой локальный чек) выполнится
   и создаст расхождение с продом.
2. Написать **новую** миграцию (`00NN_описание.sql` со следующим номером),
   которая явно отменяет/чинит эффект плохой — новый `ALTER
   TABLE`/`UPDATE`, не механический "откат".
3. Задеплоить как обычный коммит — миграция применится сама при старте
   (см. README §18). Если сама миграция **упала** при деплое — сервер не
   поднимется (`restartPolicyType: ON_FAILURE` будет ретраить старт, а не
   молча жить со сломанной схемой) — чинить тоже новым коммитом, не
   полагаться на ретраи.

## Восстановление БД из бэкапа

Postgres на Railway управляется платформой — снапшоты/бэкапы volume
настраиваются и восстанавливаются через Railway dashboard (Database →
Backups), не из этого репозитория и не кодом. Этот runbook не описывает
конкретную процедуру restore, потому что она платформенная и может
измениться независимо от кода — проверить текущие настройки retention
прямо в дашборде проекта перед тем, как полагаться на них в реальном
инциденте.

## Graceful shutdown

Реализовано (20.17.0, `src/index.ts`). На `SIGTERM`/`SIGINT` — сначала
перестаём принимать новую работу (снимаем крон-таймеры, `app.close()`
дожидается уже начатых HTTP-ответов и перестаёт принимать новые
соединения, `bot.stop()`, если polling реально шёл), потом закрываем
`pg.Pool` — порядок важен, иначе ещё летящий запрос лишится соединения с
БД посреди обработки. Жёсткий таймаут 8с — свой собственный `process.exit(1)`
раньше, чем неизвестный нам SIGKILL-таймаут Railway.

Не покрыто и не пытается быть покрытым: фоновые cron-джобы, УЖЕ начатые
до сигнала (не HTTP-запросы, внутренний тик) — их не ждём отдельно, риск
обрыва посреди работы тот же, что был всегда, graceful shutdown его не
увеличивает и не устраняет.

Живая проверка (этот способ, не `kill`/`taskkill` — на Windows сигналы
между процессами Node не доставляются в обработчик, платформенное
ограничение, не имеет отношения к проду на Linux/Railway):

```js
// process.emit() вызывает уже зарегистрированные слушатели напрямую,
// в том же процессе — то, что нужно проверить, без платформенной прослойки
process.emit('SIGTERM');
```
