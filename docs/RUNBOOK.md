## Восстановление доступа администратора

Если единственный admin потерял доступ (роль случайно понижена, аккаунт
деактивирован) — восстановление через прямой SQL, **не рутинная
операция**, только для реального инцидента:

```sql
UPDATE employees
SET access_status = 'active', is_active = true, role = 'admin'
WHERE telegram_id = <TG_ID>;
```

Через Railway → Postgres → Query (или `psql` с `DATABASE_URL` из
переменных сервиса). По правилам этого репозитория (`CLAUDE.md`) — прямая
запись в прод-БД в обход миграций требует явного подтверждения владельца
продукта, это не входит в предодобренный автономный набор действий.

## Компрометация пароля/сессии сотрудника (с MFA или без)

**Обнаружить**: подозрительные действия в `audit_log` (`actor_employee_id`,
время/характер действий, не типичные для этого человека) — с 17-layer
security hardening pass теперь включает `auth.login_success`/
`auth.login_failed`/`auth.logout`/`auth.session_revoked(_others)`, не
только смену роли/деактивацию (раньше самые auth-чувствительные события
вообще не попадали в audit_log — искать инцидент по логину/сессии было
нечем); жалоба самого сотрудника («не входил, но что-то изменилось»).

**Сдержать** — два равноценных пути, выбрать один:

- **Скрипт (предпочтительно)** — `npm run contain:employee -- --employee-id=<ID> --sessions [--mfa] [--deactivate]`
  (`backend/src/scripts/contain-compromised-employee.ts`, 17-layer
  security hardening pass). Dry-run по умолчанию — печатает план, ничего
  не меняет; добавить `--confirm` только после проверки плана. Использует
  ТЕ ЖЕ repository-функции, что и реальные API-роуты (не отдельный,
  неаудированный путь к данным) — безопаснее руками набранного SQL
  посреди инцидента (неверный id, забытый `WHERE`).
- **Прямой SQL** (если скрипт недоступен/окружение не настроено):
  1. `DELETE FROM employee_sessions WHERE employee_id = <ID>` — отзывает
     ВСЕ browser-сессии немедленно (тот же эффект, что `deleteAllForEmployee()`
     при сбросе пароля/MFA, см. `data/repositories/sessions.ts`).
  2. Если у аккаунта есть MFA (`GET /auth/mfa/status` через admin-доступ к
     БД: `SELECT * FROM employee_totp/employee_webauthn_credentials WHERE
     employee_id=<ID>`) и есть подозрение, что скомпрометирован ИМЕННО
     второй фактор (не только пароль) — `POST /employees/:id/mfa/reset`
     (admin, требует собственный step-up) отзывает TOTP/WebAuthn/recovery
     codes сотрудника целиком и его сессии заодно. `--mfa` в скрипте выше
     отзывает только Telegram AAL2-гранты, НЕ саму регистрацию факторов —
     для полного сброса регистрации нужен этот API-путь (второй admin со
     step-up), не CLI-обход этого намеренного барьера.
  3. Сброс пароля — `POST /auth/admin/reset-password/:employeeId` (admin,
     требует step-up) выдаёт одноразовую ссылку смены пароля, сама смена
     инвалидирует все сессии автоматически.

**Восстановить**: сотрудник проходит `/auth/reset/:token` (новый пароль),
при необходимости — заново включает MFA через `/auth/mfa/totp/enroll` или
`/auth/mfa/webauthn/register/options`.

**Проверить**: `SELECT * FROM audit_log WHERE target_id=<ID> AND action IN
('employee.mfa_reset','password_reset') ORDER BY created_at DESC` —
подтвердить, что сброс реально применился и когда.

## Потеря пароля или компрометация администратора без MFA

MFA (WebAuthn/TOTP/recovery codes, 20.52.0/20.52.1) с 20.52.1 обязателен
для admin/supervisor — `requireActive()` блокирует любой защищённый роут
до enrollment'а (`403 mfa_enrollment_required`), фронт при следующем
входе сам показывает экран настройки (TOTP: QR-код → код подтверждения
→ recovery-коды один раз). Если скомпрометирован admin, у которого MFA
ещё не настроен (единственный сценарий, где он вообще мог получить
полноценный доступ без второго фактора — до первого входа после
20.52.1):

1. Действовать как «Восстановление доступа (admin)» выше (прямой SQL,
   требует подтверждения владельца продукта).
2. Отдельно отозвать все его сессии (см. процедуру выше).
3. После восстановления — приложение само потребует MFA при следующем
   входе, отдельно напоминать не нужно.

Если у скомпрометированного admin УЖЕ был настроен MFA, и step-up-gated
действия (выдача роли admin, сброс чужого пароля/MFA) видны в
`audit_log` от его имени — это означает, что второй фактор тоже был в
руках атакующего (получить step-up ticket без него невозможно, см.
`docs/ADR/009`); ротация/пересоздание его MFA-факторов обязательна
(`POST /employees/:id/mfa/reset` от ДРУГОГО admin, если такой есть, иначе
прямой SQL `DELETE FROM employee_totp/employee_webauthn_credentials/
employee_recovery_codes WHERE employee_id=<ID>`).

## Ротация `BOT_TOKEN`

Компрометация токена (утёк в лог, коммит, скриншот) — токен даёт полный
контроль над ботом (отправка сообщений от его имени, чтение всех
входящих). Полноценного лога вызовов Bot API на нашей стороне нет —
Telegram не отдаёт историю запросов задним числом; то, что видно нам —
только собственный `audit_log` (действия пользователей в самом
приложении, не вызовы Bot API снаружи).

1. В [@BotFather](https://t.me/BotFather) → `/mybots` → выбрать бота →
   **API Token** → **Revoke current token**. Старый токен перестаёт
   приниматься Telegram немедленно — активная `long polling`-сессия с ним
   начнёт получать `401 Unauthorized` от Telegram API.
2. Скопировать новый токен, обновить переменную `BOT_TOKEN` в Railway
   (Variables сервиса) — сохранение переменной сама по себе передеплоя не
   требует, но новый процесс должен запуститься с ней в окружении
   (Railway обычно рестартует сервис на изменение переменных автоматически;
   если нет — форсировать redeploy вручную).
3. Убедиться, что **Replicas = 1** (см. [DEVELOPMENT.md](./DEVELOPMENT.md))
   — второй одновременный `polling` на новом токене даст тот же
   `409 getUpdates`, что и раньше.
4. Проверить `railway logs` на `🤖 Bot polling started` без ошибок сразу
   после рестарта.
5. Если есть подозрение, что токеном реально воспользовались — единственный
   доступный нам след: свериться с `audit_log` за окно компрометации на
   аномальные действия (роли, доступы) от лица настоящих пользователей —
   сам факт отправки сообщений извне через Bot API в нём не отражается,
   это ограничение Telegram, не пробел в логировании приложения.

## Ротация `ENCRYPTION_KEKS`

17-layer security hardening pass — эта процедура раньше жила только в
комментариях кода (`security/crypto/key-provider.ts`,
`scripts/backfill-support-encryption.ts`), не здесь. Компрометация
подозревается — сам KEK утёк (env-дамп, скриншот, лог) или процесс,
имевший к нему доступ, скомпрометирован (см. [THREAT-MODEL.md — угрозы
крипто-слою](./THREAT-MODEL.md#угрозы-криптографическому-слою-данных-level-2-20510),
"Компрометация работающего backend-процесса").

**Важно понимать заранее**: ротация KEK защищает только БУДУЩИЕ записи —
если сам ключ уже утёк, всё, что было зашифровано ИМ, уже читаемо тем,
кто его получил; ротация не "отзывает" прошлую утечку задним числом
(см. `docs/SECURITY.md` §10, "Rotation").

1. Сгенерировать новую версию ключа (32 случайных байта, base64):
   `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`.
2. В Railway (Variables сервиса) — добавить новую версию в `ENCRYPTION_KEKS`
   (JSON-объект `{"<версия>": "<base64-ключ>", ...}` — существующие версии
   НЕ удалять, `unwrapDek()` должен продолжать читать старые записи, см.
   `docs/SECURITY.md` §10), обновить `ENCRYPTION_ACTIVE_KEY_VERSION` на
   имя новой версии — только эта переменная решает, каким ключом
   шифруются НОВЫЕ записи.
3. Передеплоить (или дождаться авто-рестарта на изменение переменных) —
   `assertProductionEncryptionRequired()` при старте лишь проверяет, что
   шифрование вообще включено, не что конкретная версия валидна; ошибка
   в JSON `ENCRYPTION_KEKS` проявится позже, на первой попытке
   зашифровать/расшифровать — проверить `railway logs` на
   `envelope decrypt failed`/`envelope encrypt failed` сразу после
   рестарта.
4. Мигрировать уже зашифрованные записи на новый активный ключ:
   `npm run backfill:support-encryption -- --rewrap --dry-run` сначала
   (посчитать затронутые строки, ничего не менять), затем без `--dry-run`
   — находит `kid ≠ ENCRYPTION_ACTIVE_KEY_VERSION`, перешифровывает под
   новым активным ключом (`backend/src/scripts/backfill-support-encryption.ts`,
   `--rewrap`-режим, resumable/idempotent/batched, не логирует содержимое).
5. Только после того, как rewrap прошёл и подтверждён (все затронутые
   строки теперь под новым `kid`) — удалить скомпрометированную версию
   из `ENCRYPTION_KEKS` совсем. Преждевременное удаление сделает ещё не
   переехавшие строки невосстановимыми навсегда (§31 инвариант — нет
   скрытого master recovery key, см. `docs/SECURITY.md` §10).

## Миграции только вперёд, без отката

В проекте нет команды `migrate down` и никогда не было (`src/data/db/migrate.ts`
— только применение файлов по порядку, без down-скриптов). Если задеплоена
миграция, ломающая схему или данные:

1. **Не редактировать** уже применённый файл в `backend/migrations/` —
   `schema_migrations` уже пометила его применённым, повторно он не
   выполнится, а на новых окружениях (CI, чужой локальный чек) выполнится
   и создаст расхождение с продом.
2. Написать **новую** миграцию (`00NN_описание.sql` со следующим номером),
   которая явно отменяет/чинит эффект плохой — новый `ALTER
   TABLE`/`UPDATE`, не механический "откат".
3. Задеплоить как обычный коммит — миграция применится сама при старте
   (см. README §18). Если сама миграция **упала** при деплое — сервер не
   поднимется (`restartPolicyType: ON_FAILURE` будет ретраить старт, а не
   молча жить со сломанной схемой) — чинить тоже новым коммитом, не
   полагаться на ретраи.

## Восстановление БД из бэкапа

Postgres на Railway управляется платформой — снапшоты/бэкапы volume
настраиваются и восстанавливаются через Railway dashboard (Database →
Backups), не из этого репозитория и не кодом. Этот runbook не описывает
конкретную процедуру restore, потому что она платформенная и может
измениться независимо от кода — проверить текущие настройки retention
прямо в дашборде проекта перед тем, как полагаться на них в реальном
инциденте.

## Корректное завершение работы

Реализовано (20.17.0, `src/index.ts`). На `SIGTERM`/`SIGINT` — сначала
перестаём принимать новую работу (снимаем крон-таймеры, `app.close()`
дожидается уже начатых HTTP-ответов и перестаёт принимать новые
соединения, `bot.stop()`, если polling реально шёл), потом закрываем
`pg.Pool` — порядок важен, иначе ещё летящий запрос лишится соединения с
БД посреди обработки. Жёсткий таймаут 8с — свой собственный `process.exit(1)`
раньше, чем неизвестный нам SIGKILL-таймаут Railway.

Не покрыто и не пытается быть покрытым: фоновые cron-джобы, УЖЕ начатые
до сигнала (не HTTP-запросы, внутренний тик) — их не ждём отдельно, риск
обрыва посреди работы тот же, что был всегда, graceful shutdown его не
увеличивает и не устраняет.

Живая проверка (этот способ, не `kill`/`taskkill` — на Windows сигналы
между процессами Node не доставляются в обработчик, платформенное
ограничение, не имеет отношения к проду на Linux/Railway):

```js
// process.emit() вызывает уже зарегистрированные слушатели напрямую,
// в том же процессе — то, что нужно проверить, без платформенной прослойки
process.emit('SIGTERM');
```

## Состояние, готовность и метрики (20.32.0)

Четыре разных эндпоинта, каждый отвечает на свой вопрос — не путать между
собой при настройке внешнего мониторинга:

- **`GET /health`** — исторический, оставлен как есть (совместимость с уже
  существующими скриптами/дисциплиной сессии). Не завязан ни на что.
- **`GET /healthz`** — жив ли процесс. `{"status":"ok"}`, без обращения к
  БД/Telegram/AI. Годится для liveness-проверки контейнера (перезапустить,
  если это упало) — но НЕ для решения "слать ли сюда трафик", база может
  быть временно недоступна, а процесс всё ещё жив.
- **`GET /readyz`** — может ли ЭТОТ инстанс обслуживать запросы прямо
  сейчас. `200 {"status":"ready"}` или `503` с причиной:
  `{"status":"not_ready","reason":"bootstrap_incomplete"}` (ещё не
  завершился `buildApp()` — на практике не должно случаться после
  `app.listen()`) или `{"status":"not_ready","reason":"database_unreachable"}`
  (живой `SELECT 1` не прошёл). Годится для readiness-проверки
  (снять с балансировки, не перезапускать) — если завтра появится больше
  одной реплики.
- **`GET /integrations/health`** — конфигурация Telegram/AI (только
  наличие env-переменных, без единого живого запроса к самим сервисам).
  Диагностика, не для автоматического мониторинга.
- **`GET /metrics/system`** — Prometheus exposition format (`prom-client`).
  Не `/metrics` — та строка занята бизнес-каталогом кастомных метрик
  (`api/routes/metrics.ts`, существует с ранних версий проекта); коллизия
  между ними ронялa регистрацию business-модуля целиком, молча, с самого
  появления этого Prometheus-эндпоинта — найдено и разведено security-
  аудитом 20.52.1 (`registerAllRoutes()` теперь падает громко на такую
  коллизию, а не глотает её). Никто не обязан scrape'ить `/metrics/system`
  постоянно — сама возможность есть уже сейчас, коллектор подключается
  отдельно, когда понадобится. Четыре группы: `http_*` (route — паттерн,
  не резолвнутый URL), `db_*` (агрегатно), `jobs_*` (по имени джобы),
  `ai_*` (по operation) — плюс стандартные Node.js process-метрики от
  `collectDefaultMetrics()`.

Живая проверка:

```bash
curl https://tele2-app-production.up.railway.app/healthz
curl https://tele2-app-production.up.railway.app/readyz
curl https://tele2-app-production.up.railway.app/metrics/system | head -50
```
