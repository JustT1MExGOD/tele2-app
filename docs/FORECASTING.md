# Прогноз продаж: как это работает и насколько точно

[Документация](README.md) · [Обзор проекта](../README.md)

«Прогноз» точки, подсказки по штату), какими методами измеряется её

## Два разных прогноза в одном коде

`core/analytics/forecast.ts` считает один и тот же числовой прогноз
дня — `projectDay()` поверх модели `buildSesModel()` — но используется
он в двух разных задачах с разной чувствительностью к ошибке:

| Где | Что показывает | Функция |
| --- | --- | --- |
| Страница «Прогноз» точки, подсказки по штату | Прогноз на каждый из следующих N дней по отдельности | `forecastStore()` (`core/analytics/forecast.ts`) |
| Кабинет супервайзера — «выполнение плана к концу месяца» | Один итог: факт с начала месяца + прогноз оставшихся дней | `forecastRemainingOfMonth()` (`core/analytics/supervisor.ts`) |

До 21-й эпохи оба места суммировали прогноз день-за-днём одной и той же
SES-моделью. Сейчас это разошлось: **поштучный прогноз дня** по-прежнему
SES, а **итог месяца** считается run-rate (см. ниже) — потому что
backtest показал, что для суммы за много дней вперёд плоский пейс
точнее, чем сумма пошаговых прогнозов с сезонностью.

## Прогноз одного дня — SES с сезонностью

Модель — экспоненциальное сглаживание уровня с демпфированным трендом
(Holt/Gardner-McKenzie) и мультипликативной сезонной поправкой на день
недели с усадкой (shrinkage) к нейтральной 1.0, пока по этому дню
недели мало наблюдений. Код и константы — `buildSesModel`/`projectDay`
в `core/analytics/forecast.ts:80-179`, там же подробный разбор, почему
именно такая форма (см. комментарии у констант `ALPHA/BETA/PHI/SHRINK_K`).

Коротко:

- **Уровень** — обычное SES: `level = α·факт + (1-α)·(level + φ·trend)`.
- **Тренд** — демпфированный Holt: экстраполируется не `trend×шаги`, а
  суммой `φ + φ² + ... + φʰ` — иначе на горизонте 25+ дней линейный
  тренд уводит прогноз в отрыв от реальности.
- **Сезонность** — средний ratio факт/уровень по дню недели, с усадкой
  `(cnt·raw + SHRINK_K·1) / (cnt + SHRINK_K)` — при малом числе
  наблюдений по дню недели поправка близка к 1.0 (модель ведёт себя как
  чистое SES), при накоплении истории — уточняется.
- Окно истории — 120 дней, с явным дозаполнением пропущенных дней
  нулями (иначе сглаженный уровень никогда не видит настоящий 0 и
  застревает на случайном высоком дне — реальный баг, найденный на
  денежных метриках).

`ALPHA=0.3, BETA=0.05, PHI=0.9, SHRINK_K=7` подобраны grid-search'ем по
реальным историческим чек-поинтам
(`backend/src/scripts/forecast-month-backtest.ts --grid-search`), а не
на глаз. `SHRINK_K` намеренно не поднят выше 7, хотя более широкий
поиск показывал дальнейший рост точности по SMAPE — при `SHRINK_K→∞`
поправка на день недели вырождается в 1.0 для всех дней, и модель
перестаёт замечать настоящие аномалии (проверено: `SHRINK_K=10` ломает
`tests/isolation/anomaly.test.ts`).

Эта SES-модель по-прежнему считает **день-в-день прогноз** (страница
точки, подсказки по штату) и **доверительный интервал** (см. ниже) — там
она остаётся лучшим найденным методом.

## Прогноз остатка месяца — run-rate

`forecastRemainingOfMonth()` (`core/analytics/supervisor.ts`) отвечает
на вопрос «сколько будет в сумме к концу месяца», а не «сколько будет
именно в четверг». Для этого вопроса SES-сумма по дням проигрывает
плоской линейной экстраполяции пейса:

```
пейс_в_день = факт_с_начала_месяца / прошедшие_дни
остаток     = пейс_в_день × оставшиеся_дни
итог месяца = факт_с_начала_месяца + остаток
```

Это не отменяет SES-модель полностью — она всё ещё строится для
`stdev`/доверительного интервала (нужен разброс по дню недели), просто
точечная оценка суммы больше не берётся из неё.

Почему так: backtest на 748 реальных чек-поинтах (точка × месяц × день
контроля 5/10/15/20/25, `--runrate-check`) показал, что run-rate точнее
SES-суммы **на каждом горизонте** и **на каждой из метрик по
отдельности**, не только в среднем:

| Метод | SMAPE (748 чек-поинтов) |
| --- | --- |
| SES, сумма `projectDay` по дням | 5.01% |
| Run-rate (факт/прошедшие × оставшиеся) | 3.94% |

Интуиция: за 5-25 дней текущего месяца в факте уже сидит вся реальная
информация о том, как сейчас идут дела в точке (акции, штат, сезон) —
экстраполировать её напрямую надёжнее, чем сначала сжать в
120-дневную сглаженную модель, а потом растягивать обратно на 25+ дней
вперёд одним днём за раз.

## Доверительный интервал

`projectDayInterval()`/`projectDayStdev()` (`core/analytics/forecast.ts`)
дают `predicted ± CONFIDENCE_Z·σ` для одного дня, `CONFIDENCE_Z=1`.
`σ` — `level × spread[dow]`, с полом `20%` от уровня (иначе дни без
истории по конкретному dow дают ложно узкий диапазон). Для месячного
интервала (`supervisor.ts`) дисперсии дней складываются (дни считаются
независимыми), затем берётся корень — так интервал на 25 дней вперёд
не оказывается неправдоподобно широким (сумма стандартных отклонений
вместо суммы дисперсий).

## Как измеряется точность

Метрика — **SMAPE** (symmetric mean absolute percentage error):
`2·|прогноз - факт| / (|прогноз| + |факт|)`, усреднённая по всем
чек-поинтам. В отличие от обычного MAPE, она определена даже при
факте = 0 (частый случай для редких метрик вроде `combo`). В интерфейсах
показывается «Точность» = `100% - SMAPE%`.

Скрипт: `backend/src/scripts/forecast-month-backtest.ts`. Метод —
скользящее окно по реальным историческим данным (read-only,
`DATABASE_URL` из `backend/.env.test`, прод-прокси Railway, без записи):

1. Берутся все точки сети и все завершённые календарные месяцы в
   истории.
2. На каждый чек-поинт (день 5/10/15/20/25 месяца) строится модель
   строго по 120 дням, предшествующим этому дню — то же окно, что
   `forecastStore`/`forecastRemainingOfMonth` используют в проде.
3. Прогнозируется итог месяца, сравнивается с уже случившимся
   фактическим итогом.
4. SMAPE усредняется по всем парам (чек-поинт × метрика) с равным
   весом — это единственное число, по которому сравниваются гипотезы.

Режимы скрипта:

| Флаг | Что показывает |
| --- | --- |
| (без флагов) | Отчёт по чек-поинтам 5/10/15/20/25 × метрикам sim/mnp/pa/combo — тот метод, который реально работает в проде |
| `--grid-search` | Перебор `ALPHA/BETA/PHI/SHRINK_K` по сетке — как подобраны константы `forecast.ts` |
| `--grid-search-per-metric` | Проверка гипотезы «настроить константы отдельно на каждую метрику» |
| `--window-search` | Сравнение размера окна истории (60/90/120/150/180/240 дней) на честном общем пересечении чек-поинтов |
| `--cold-start` | Разбивка точности по объёму реальной истории точки (молодые vs зрелые) |
| `--runrate-check` | Сравнение SES-суммы, run-rate и альтернативных гипотез (см. ниже) — источник решения перейти на run-rate |

Отдельный скрипт `forecast-backtest.ts` меряет **прогноз одного дня
вперёд** (не итог месяца) тем же скользящим окном, включая
`--holiday-check` — сравнение точности на известные праздничные даты
против соседних будних дней.

Оба скрипта read-only, требуют переменную окружения `DATABASE_URL`
(обычно — прокси из `backend/.env.test`, см. `CLAUDE.md`).

## Текущая точность

Историческое подтверждение (748 чек-поинтов, снято 2026-09-12,
`forecast-month-backtest.ts` без флагов, метод — run-rate):

| Когда смотрим | Точность | SMAPE |
| --- | --- | --- |
| День 5 | 92.8% | 7.2% |
| День 10 | 94.5% | 5.5% |
| День 15 | 96.3% | 3.7% |
| День 20 | 97.8% | 2.2% |
| День 25 | 98.4% | 1.6% |
| **Итого по всем точкам** | **96.06%** | **3.94%** |

Закономерность стабильна для всех проверенных версий модели: чем
раньше в месяце строится прогноз, тем он менее точен — это
математическое следствие экстраполяции на больший горизонт по меньшему
объёму данных текущего месяца, не артефакт конкретного метода.

## Что проверялось и не прижилось

Каждая строка — отдельный эксперимент в `--runrate-check` или
соответствующем флаге, отклонён по фактическому результату backtest, не
на глаз:

| Гипотеза | Результат | Вывод |
| --- | --- | --- |
| Настроить `ALPHA/SHRINK_K` отдельно на каждую метрику (`--grid-search-per-metric`) | 9.14% против 5.01% у общих констант | Хуже — общий `BETA` (тренд) важнее индивидуальной настройки, отдельная настройка теряла тренд-компоненту |
| Увеличить окно истории со 120 до 150/180 дней (`--window-search`) | ~0.15pp выигрыша на маленькой шумной выборке | Не стоит риска переобучения, оставлено 120 |
| Молодые/недавно импортированные точки — источник просадки точности (`--cold-start`) | Просадка объясняется 2 конкретными «зрелыми» точками с падающим трендом, не возрастом истории | Не подтвердилось, изменений не внесено |
| Прогноз хуже на праздничные даты (`--holiday-check`) | Один подтверждённый случай (1 января, магазины закрыты) — но только 1 наблюдение на праздник за всю историю | Недостаточно данных для калибровки без риска переобучения на одно наблюдение |
| Бленд SES-суммы и run-rate в любой пропорции | Монотонно хуже по мере роста доли SES — чистый run-rate (0% SES) всегда лучший | SES для итога месяца не нужен вообще, даже частично |
| Средняя историческая доля месяца, накопленная к чек-поинту (`factToDate / avgFraction`), даже in-sample | 4.14% — хуже run-rate (3.94%) | Усреднение по всей сети смазывает то, что уже видно в факте конкретной точки |
| Пейс за последние N дней вместо всего месяца с начала | Хуже при любом N (3-30 дней), тем хуже, чем короче N | Полный факт месяца — лучший якорь, короткое окно ловит только шум |
| Байесовская усадка пейса к SES-уровню (`k` псевдо-дней) | Скачок SMAPE 3.94% → 9.27% уже при `k=0.5` | SES-уровень как якорь резко хуже сырого факта — не смешивать |
| Поправка на состав дня недели (seasonal остатка/прошедшего) | 3.94% — статистически неотличимо от чистого run-rate | Не даёт измеримого выигрыша, добавлять не стали — меньше кода лучше |
| Усечение (winsorizing) дневного факта перед усреднением пейса | 3.98-4.27% — хуже, тем больше, чем туже клэмп (1.5×→4.27%, 2×→4.18%, 3×→4.09%, 5×→3.98%) | Клэмп режет не выбросы, а обычную вариативность малой выборки — монотонно вредит, чем ближе к no-op, тем меньше вред |
| Бленд пейса с фактом предыдущего календарного месяца той же точки | Скачок SMAPE 3.94% → 6.50% уже при `k=1` | Месяц-к-месяцу дрейф (акции, штат) делает соседний месяц плохим якорем |
| Поправка на систематическое отклонение точки (leave-one-out бленд факт/прогноз по остальным чек-поинтам той же точки и метрики, `--store-bias-check`) | Лучший вариант — зажим 1× (no-op) = базовые 3.94%; более широкий зажим только хуже (1.2×→4.03%, 1.5-3×→4.16%) | Устойчивого per-store смещения в данных нет, поправлять нечего |
| Медиана дневных значений с начала месяца вместо среднего как пейс (`--median-pace-check`) | 4.82% против 3.94% — хуже на КАЖДОМ чек-поинте (д5=8.48%, д10=6.76%, д15=4.62%, д20=2.80%, д25=1.83%) | При малом числе прошедших дней медиана — слишком грубая оценка типичного дня; среднее использует всю информацию |
| Экспоненциально взвешенный пейс — EWMA по дням месяца, недавние дни весят больше (`--weighted-pace-check`) | decay=0.9-0.92 → 3.91% против 3.94% у плоского среднего — на 0.03pp лучше, но выигрыш даёт только д20/д25 (2.03%/1.54% против 2.16%/1.59%), а д15 чуть хуже (3.78% против 3.71%) | Улучшение на грани шума при 748 чек-поинтах — тот же случай, что `--window-search` (0.15pp): слишком маленький и неравномерный эффект, чтобы усложнять прод-формулу и рисковать переобучением |
| Линейная OLS-регрессия дневного факта по номеру дня месяца, экстраполяция тренда (`--trend-regression-check`) | 6.37% против 3.94% — заметно хуже, катастрофично на д5 (14.07%) | Линейный тренд на 5-15 шумных точках даёт неустойчивый наклон и разносит экстраполяцию на ~20 дней вперёд; чем сложнее модель, тем сильнее она переобучается на коротком окне |
| Ансамбль: усреднение run-rate + EWMA(0.9) + SES-суммы (`--ensemble-check`) | Любая примесь SES (соло 5.01%) тянет ансамбль вниз; run-rate+EWMA пополам даёт 3.92% — между двумя одиночными методами, без выигрыша сверх лучшего | Run-rate и EWMA считаются по одному и тому же факту месяца — слишком коррелированы, ансамблю нечем диверсифицировать ошибки |
| Исключение аномальных дней (z≥2 к SES-уровню, тем же порогом, что детектор аномалий) из усреднения пейса (`--anomaly-exclude-pace-check`) | 4.28% против 3.94% — хуже; исключено 1.3% дней (576 из 45560) | Помеченные дни чаще редкий, но реальный спрос, а не шум — их исключение теряет сигнал, а не убирает помеху |
| Пейс напрямую по дню недели остатка, без SES-сезонности (`--dow-direct-pace-check`) | 3.95% — статистически неотличимо от run-rate (3.94%) | Раскладка по дням недели не добавляет сигнала сверх того, что уже есть в простом среднем |
| Сетевой день-фактор: отклонение всей сети (не одной точки) за последние 7 прошедших дней применяется как множитель к прогнозу каждой точки (`--network-factor-check`) | 3.93% против 3.94% — выигрыш на грани шума, того же масштаба, что EWMA | Не стоит усложнения ради статистически неразличимого эффекта |
| Калибровка доверительного интервала: сравнение покрытия ±1σ у текущего прод-варианта (SES stdev), run-rate-согласованного (разброс прошедших дней) и bootstrap-ресэмплинга (`--interval-check`) | Покрытие 94.5% / 93.5% / 93.5% соответственно (при номинальных ~68% для z=1) — все три метода дают похожий, стабильно широкий интервал | Несостыковка «точка — run-rate, интервал — SES» не портит калибровку на практике; менять stdev-источник не требуется |
| Устойчивость ранжирования run-rate vs EWMA(0.9) к схеме взвешивания чек-поинтов: равный вес / ранние важнее (1/checkpointDay) / поздние важнее (checkpointDay) (`--weighted-metric-check`) | EWMA стабильно чуть лучше run-rate при любой схеме (разница 0.01-0.04pp) | Направление эффекта устойчиво, но величина остаётся на уровне шума при любом взвешивании — не меняет решение не внедрять EWMA |

Итог всех экспериментов: **факт с начала текущего месяца, без сглаживания
и без примеси других источников — лучший найденный предиктор** итога
месяца. Любая попытка «умнее» скорректировать пейс (сезонностью, чужим
месяцем, сглаженным уровнем) на реальных исторических чек-поинтах
только портила SMAPE.

## Известные пределы

- **День 5 — фундаментальный потолок, не баг.** Экстраполяция на ~25
  дней вперёд по 5 дням факта инерционно шумная у любого метода — это
  подтверждено на SES, run-rate и всех проверенных гибридах. Точность
  92.8% на этом горизонте — не хуже, чем позволяет сама задача с
  текущим объёмом данных.
- **`combo` — самая шумная метрика** (низкий объём, лумпи-распределение)
  — SMAPE выше, чем у sim/mnp/pa на любом горизонте. Ожидаемо для
  низкочастотной метрики, не повод менять модель под неё отдельно
  (см. провал per-metric настройки выше).
- **Праздничные даты** прогнозируются хуже (см. таблицу выше), но
  калибровать это пока не на чем — по одному наблюдению на каждый
  праздник за всю историю данных. Пересмотреть после накопления 2+
  циклов по каждой праздничной дате.
