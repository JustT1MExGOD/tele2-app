# 20.54.0 — Security Hardening & Defense in Depth

Baseline: tracked HEAD at start of this pass was `48032cf` / package
version `20.53.0` (verified via `git status --short`, `git log -1
--oneline`, `git ls-files`, `cat backend/package.json` — no legacy

This document records genuine findings from this pass — confirmed by
reading the actual code, not carried over from any external report —

(with tests) rather than making shallow, unverified changes across all

## Fixed this pass

### P1-A — Distributed (Postgres-backed) rate limiting

**Finding.** Every rate-limited route (`app.ts` global limiter, and every
per-route `config.rateLimit`) uses `@fastify/rate-limit`'s default
in-memory store. Counters are lost on every restart/deploy, and would
not be shared if this service ever ran more than one replica. Today the
Telegram bot's long-polling (`grammy`) requires exactly one replica
(`docs/RUNBOOK.md`), so the "multiple instances" half of the original
concern does not currently apply — but the "restart wipes brute-force
counters" half does, on every deploy.

**Fix.** New module `backend/src/security/rate-limit.ts` — Postgres-backed
fixed-window counters (`security_rate_limit_counters`, migration
`0025_security_rate_limit.sql`), `consume(dimensions[])` checks/increments
multiple identity axes (IP + account/identity-hash) atomically, fails
closed (denies only the current request, writes nothing) on storage
failure so no permanent lockout can result from a transient DB error.
Applied as a second layer alongside the existing per-route in-memory
limiter (not a replacement — defense in depth) on: `POST /auth/login`,
`POST /auth/reset/:token`, `POST /auth/login/mfa`, `POST
/auth/mfa/step-up`, `POST /auth/mfa/telegram/verify`, `POST
/auth/mfa/totp/confirm`.

**Trade-off, documented not hidden.** Fixed-window counters allow up to
~2x burst right at a window boundary — not addressed with a
sliding-window log, since the threat model here (TOTP/password/recovery-
code brute force needs thousands of guesses) doesn't make that slop
meaningful. Not yet applied to every rate-limited route in the app
(WebAuthn registration options, avatar upload, forecast/AI endpoints,
etc.) — scoped to the credential-verification surface the brief
prioritized (§56, P1-A first).

**Tests.** `tests/isolation/rate-limit.test.ts` — module-level
consume()/blocking/multi-dimension semantics, plus one HTTP-level
regression on `/auth/login`.

### P1-F — CSV formula injection

**Finding.** The existing `csvEscape()` in `api/routes/ops/export.ts`
only quoted delimiter/quote/newline characters. It never guarded against
formula injection: an admin-entered employee or store display name
starting with `=`, `+`, `-`, or `@` is interpreted as a formula by
Excel/LibreOffice/Sheets when the exported CSV is opened. All three CSV
export routes (`/export/sales.csv`, `/export/bfq.csv`,
`/export/schedules.csv`) include at least one such field.

**Fix.** New `backend/src/security/csv-safe.ts` — `csvSafeCell()`
prefixes a leading apostrophe (the standard OWASP mitigation; both
Excel and Sheets render it as literal text, not part of the value) for
any cell starting with `=`/`+`/`-`/`@`/tab/CR, then applies the existing
quoting. Wired into all three export routes, replacing the local
`csvEscape()`. Also added `safeFilenameSegment()` and applied it to the
`from`/`to`/`month` values interpolated into `Content-Disposition`
filenames (previously unvalidated query values; Node already rejects
raw CR/LF in header values, this closes the remaining gap — stray
quotes/non-ASCII/path separators — rather than relying on that alone).

**Tests.** `tests/isolation/export.test.ts` — new `CSV formula
injection (§P1-F)` describe block: formula-like employee/store names
neutralized on both `/export/sales.csv` and `/export/bfq.csv`, plus a
regression that normal Cyrillic/UTF-8 names still pass through
unmodified (no false-positive escaping).

### P1-G — Offline queue account isolation

**Finding, split in two:**

1. Server side (`POST /sync/batch`, `api/routes/shifts.ts`) — **already
   correct**, verified by reading the code and by existing test coverage
   (`tests/isolation/quick-sale-sync.test.ts`): a non-manager cannot sync
   an op whose `employee_id` differs from `request.user.employee_id`, and
   `assertStoreInOrg` still applies. This was a real bug in a much
   earlier release (see the changelog entry for v20.11.1's audit) and was
   already fixed and regression-tested before this pass — re-confirmed,
   not re-fixed.

2. Client side (`frontend/offline-queue.js`) — **a real, unfixed gap**.
   The queue is a single browser-wide IndexedDB store, never scoped to a
   session/identity, and neither logout path
   (`frontend/src/pages/my-plan/index.ts::logoutSelf`,
   `frontend/src/pages/access-supervisor/index.ts::logoutFromMfaGate`)
   cleared it before reloading. Concrete scenario: employee A queues an
   offline sale on a shared device, logs out before the network returns,
   manager B logs into the same device, network comes back — the
   `online` listener / 30s interval in `offline-queue.js` flushes A's
   still-pending op using B's now-current session. Because B is a
   manager (`canWriteSalesForOthers`), the server-side check above does
   **not** reject it — B's session would silently submit A's stale
   queued sale. (A non-manager B is safe today only because the server
   rejects it, but the op then lingers in the queue indefinitely,
   retrying and failing on every flush — a real papercut on top of the
   isolation gap.)

**Fix.** Added `OfflineQueue.clear()` to `frontend/offline-queue.js`.
Both logout paths now: best-effort `flush()` while the session is still
valid (don't silently lose a genuinely-the-same-user's pending sale),
then unconditionally `clear()` before the actual `/auth/logout` call and
page reload — so nothing queued under the outgoing identity can survive
to replay under the next one.

**Tests.** Frontend-only fix; this project has no browser/E2E harness
for the Mini App (same situation as the 20.52.1 MFA frontend UI —
verified by code reading, not automated browser test). The server-side
half already has full regression coverage (see above), which is the
half that determines whether a mis-replayed op could actually be
accepted.

### P1-H — MINI_APP_URL required in production (config validation)

**Finding.** `auth/csrf.ts::expectedOrigin()` returns `''` when
`MINI_APP_URL` is unset. `requireCsrf()`'s Origin-header check is gated
on `if (origin && expected && ...)` — an empty `expected` silently
**disables** that check rather than failing closed. (The independent
double-submit cookie/header token check still runs regardless, so this
was never a full CSRF bypass — but a defense-in-depth layer silently
degrading on missing config is exactly the class of bug fail-closed
startup validation exists to catch before deploy, not after.)
`auth/mfa/webauthn.ts` already fails closed correctly when
`MINI_APP_URL` is unset (`isWebAuthnConfigured()` → 503), so only the
CSRF side needed a fix.

**Fix.** New `backend/src/config/validate.ts` —
`validateProductionConfig()` requires `MINI_APP_URL` to be set and a
valid `https://` URL. Wired into `index.ts`'s existing production-guard
block (same `alertAndExit()` fail-closed pattern as `BOT_TOKEN` and the
encryption checks) — added alongside those, not replacing them.

**Trade-off, documented not hidden.** This is a single, high-value
addition to config validation, not the full "centralized schema"
(DATABASE_URL, AI config, cookie security, trusted-proxy topology, etc.)
the brief describes — see "Deferred" below. `trustProxy: 1` (`app.ts`)
and client-IP usage were separately audited (grepped every
`request.ip`/audit-log call site) and confirmed correct for Railway's
actual single-hop topology and used only in the new rate limiter — no
change needed there.

**Tests.** `tests/unit/config-validate.test.ts` — unset/invalid/non-
https/valid cases for `validateProductionConfig()`.

### P1-B — WebAuthn ceremony hardening (test coverage, no code bug found)

**Audit.** Read `auth/mfa/webauthn.ts` and `data/repositories/mfa.ts`'s
`createWebAuthnChallenge`/`consumeWebAuthnChallenge` in full.

- **CSPRNG/entropy** — delegated entirely to `@simplewebauthn/server`'s
  `generateRegistrationOptions()`/`generateAuthenticationOptions()`, not
  custom code. No finding.
- **TTL** — 5 minutes, hardcoded in the `INSERT`. No finding.
- **Atomic single-use consume** — `UPDATE ... WHERE ... consumed_at IS
  NULL ... RETURNING`, same pattern already proven race-safe for
  TOTP/pending-login/recovery-codes elsewhere in this codebase. Verified
  with a new concurrent test (below), not just re-read.
- **Purpose binding across register/authenticate** — hard DB-level
  separation (`kind` column, `CHECK (kind IN ('register','authenticate'))`),
  correctly enforced. No finding.
- **Purpose binding *within* 'authenticate'** (login-MFA vs. step-up vs.
  Telegram-AAL2-verify all share `kind='authenticate'`) — investigated in
  depth, including writing a test that initially asserted the *wrong*
  behavior and had to be corrected against what the code actually does
  (see `tests/isolation/webauthn-challenges.test.ts`). Finding: this
  repository layer does **not** itself guarantee "the right challenge for
  the right ceremony" — if two `authenticate` challenges are pending for
  one employee, `consumeWebAuthnChallenge()` hands out whichever is most
  recent on each call, newest first, regardless of which physical
  ceremony is asking. This is **not exploitable** — the actual challenge
  match is enforced independently at the cryptography layer
  (`verifyAuthenticationResponse()`'s `expectedChallenge` comparison
  against the signed `clientDataJSON`), so a mismatched hand-out can only
  ever cause a legitimate concurrent ceremony to fail closed, never a
  wrongful acceptance. Documented as a known usability edge case (two
  browser tabs / overlapping login+step-up for the same employee may
  transiently interfere), not fixed — fixing it would mean threading a
  ceremony-specific correlation id through three different route
  handlers for a case that fails safe today.
- **Counter/clone-detection** — `verifyAuthenticationResponse()` is
  passed the stored `counter` and internally rejects a counter that goes
  backward (standard clone-detection), except when an authenticator
  reports `counter=0` (many platform authenticators, e.g. Touch ID/
  Windows Hello, don't implement counters — the library's own documented
  exemption). Confirmed as library-internal behavior, not re-implemented
  — no finding, no code change (per §4: never write custom WebAuthn
  verification logic).

**Fix.** No production code changed — this was a coverage gap, not a
bug. New `tests/isolation/webauthn-challenges.test.ts` (5 tests):
concurrent single-use consume (the "parallel ceremony" test the brief
asked for), expiry, kind separation, employee scoping, and the
newest-first multi-pending-challenge behavior above, with the safety
reasoning written into the test itself so it doesn't silently regress
into an actual bypass if the crypto-layer check is ever changed.

### P1-C — Tenant/supervisor IDOR audit

**Audit.** Systematic pass (via a dedicated research pass covering every
route under `api/routes/**` with a `:id` param, every PATCH/DELETE/PUT,
and all repository query paths) found the codebase already solid — three
prior hardening passes (20.50.0, 20.52.0, 20.53.0) had already closed the
real gaps. Two routes initially looked like findings:
`GET /stores/:id/profile` (`api/routes/profiles/store.ts`) and `GET
/employees/:id/profile` (`api/routes/profiles/employee.ts`) — both check
org membership but not supervisor-sector membership, unlike
`core/analytics/supervisor.ts`'s `resolveSupervisorStores()`.

**Investigated further, not fixed — this is a reviewed product-scope
question, not a bug.** Sector-based scoping (`supervisor_sectors` →
`getUserStoreIds()`/`resolveSupervisorStores()`) is, in the CURRENT
product, applied **only** to dashboard-aggregate views (Command Center,
the supervisor's own dashboard) — not to baseline visibility.
`GET /employees` (the whole team roster), `GET /stores` (the whole store
list), and `/sales/history` all already return org-wide data to a
supervisor today, not sector-filtered. Patching just the two profile
routes would be inconsistent (the same underlying data is already
reachable through those other, already-existing, unrestricted routes)
and wouldn't close any real exposure. Whether "sector" should become a
hard confidentiality boundary across the whole app — team roster, store
list, sales history, profiles, everything — is a product decision (does
a supervisor covering a colleague's sector, or just checking a sibling
sector's numbers for context, need to keep working?), not something to
decide unilaterally as a security patch. **Confirmed with the product
owner during this pass: document as-is, do not change.** `getUserStoreIds()`
in `auth/guards.ts` is genuinely unused dead code (its own doc comment
points to a legacy file that no longer exists) — left alone, not removed,
since deleting it isn't what this pass is about.

### P1-D — Support confidentiality + encryption key rotation

**Audit.** Read `data/repositories/support.ts` and `api/routes/ops/support.ts`
in full.

- **Cross-tenant leakage** — `support_tickets`/`support_messages` have no
  `org_id` column at all, and `requireAdmin()` in the route file checks
  `role === 'admin'` globally, not per-org. Confirmed this is by design,
  not a leak: `admin` is the single top-of-hierarchy role for the whole
  deployment (orgs here are internal network divisions of one company,
  not separate tenant companies — true multi-client isolation is an
  unbuilt future epic per the product roadmap), so an admin seeing every
  org's support tickets is the same trust level as an admin already
  seeing every org's data everywhere else in the app. No finding.
- **Ownership checks** — both `GET`/`POST /support/tickets/:id/messages`
  correctly gate on `isAdmin || isOwner` (telegram_id or employee_id
  match) before returning ticket detail or accepting a reply. No finding.
- **Telegram plaintext leak** — `notifyAdmin()`/`notifyUser()` send
  ticket text to Telegram in plaintext. Already explicitly documented in
  the file's own header comment as an accepted, inherent trade-off (an
  admin has to read the message to answer it — that's the feature, not a
  bug) — not re-litigated here.
- **Legacy plaintext rows** — read-only production check (see below)
  found real plaintext rows sitting in the DB right now, unaddressed by
  any prior pass. This is the one genuine, actionable gap.

**Read-only production check** (pre-approved per CLAUDE.md — investigation
only, no writes): `support_tickets` has 8 rows, **all 8 unencrypted**
(`message_encrypted IS NULL`); `support_messages` has 2 rows, **both
unencrypted**. All 10 rows date to a single day (2026-08-01), consistent
with predating encryption being turned on in production rather than any
bug — `employee_totp` (1 row) IS encrypted, confirming
`DATA_ENCRYPTION_ENABLED` is genuinely active today and new writes are
protected; it's specifically these pre-existing rows that were never
migrated. This matches exactly the already-documented, intentional
"historical plaintext boundary" behavior in `support.ts`'s own comments
— not a new bug, but a real, live, unaddressed exposure worth actually
closing rather than leaving as a permanent asterisk.

**Fix — built, tested locally, deliberately NOT run against production
this pass** (same reasoning as the rate-limit/CSV/config work: this repo's
discipline requires a separate explicit confirmation for any direct
production write outside the migration system, and this is exactly that
kind of write). New `src/scripts/backfill-support-encryption.ts`:

- **Backfill mode** (default) — encrypts every plaintext
  `support_tickets.message`/`admin_reply` and `support_messages.body`
  row under the current active key, using the exact same AAD context
  shape the app's own decrypt path expects. Resumable/idempotent (only
  ever touches rows where `*_encrypted IS NULL`, each UPDATE re-checks
  that same condition), batched (default 100 rows/pass, loops until
  none left — never one giant transaction), observable (prints ids/counts
  per batch), never logs message content.
- **`--rewrap` mode** — closes the other half of the P1-D ask (key
  rotation). `ENCRYPTION_KEKS`/`ENCRYPTION_ACTIVE_KEY_VERSION`
  (`security/crypto/key-provider.ts`) already supported multiple key
  versions simultaneously before this pass — rotating is already just
  "add a new version, flip the active pointer," and old ciphertext keeps
  decrypting via the old version staying in `ENCRYPTION_KEKS`. What was
  missing: a way to actually migrate EXISTING rows off a retiring key so
  it can eventually be dropped. `--rewrap` finds every row whose
  envelope's `kid` isn't the current active version, decrypts under
  whichever version it names, re-encrypts under the active one — same
  batched/idempotent/no-plaintext-logs discipline.
- **`--dry-run`** on both modes — scans and reports without writing.

**Tests.** `tests/isolation/backfill-support-encryption.test.ts` (4
tests, all against the local test DB, not production): plaintext →
encrypted with byte-exact round-trip through the real
`findTicket`/`listMessages` repository functions (not just "an envelope
exists"), idempotency on re-run, dry-run never mutates, and a full
key-rotation simulation (encrypt under key A, rotate active to key B
while A stays known, rewrap, confirm the envelope's `kid` is now B and
the plaintext is unchanged, confirm a second rewrap is a no-op).

**Manual action available, not taken**: `npm run backfill:support-encryption`
(add `-- --dry-run` first to preview, `-- --rewrap` for the key-rotation
mode) against production would encrypt those 10 existing plaintext rows.
Left for the product owner to run explicitly.

### P1-E — Frontend XSS sink audit

**Audit.** Systematic pass over every `innerHTML`/`outerHTML`/
`insertAdjacentHTML`/`document.write`/`DOMParser`/dynamic-`href`-or-`src`
usage across `frontend/src/**`. Three prior passes (20.49.0, 20.50.1, and
ongoing per-feature fixes) had already closed most of the reachable
sinks — support tickets/FAQ, tasks, announcements, access-requests,
dealers/sectors, BFQ, alerts, store/employee profiles all correctly
`esc()` every freeform field. No unsafe URL-scheme handling found
anywhere (`javascript:`/`vbscript:`/inappropriate `data:` — none of the
dynamic `href`/`src` assignments in the codebase take attacker input;
the only dynamic ones are `URL.createObjectURL()` on local blobs and an
API-constructed avatar URL keyed by numeric employee id). No
`DOMParser`, no dynamic `<script src>`, no homemade regex sanitizer.

**Found — a real, repeated pattern, not one-off bugs.** `shift_text`
(the free-text shift label managers set in the schedule) and
`store_name` were escaped correctly in `pages/schedule/index.ts` but
rendered **raw** in four sibling files that pull the exact same
API-response fields: `pages/home/index.ts`, `pages/my-plan/index.ts`,
`pages/team/index.ts`, `pages/shift/index.ts`. Same root cause each
time — the field was already being escaped somewhere else in the
codebase, just not at every render site. Two more, same class:
`home/index.ts`'s greeting-card `firstName` (from admin-entered
`full_name`) and `features/promos/index.ts`'s `mask` (first/last 2 chars
of the admin-entered promo code survive server-side masking — low
practical severity since only 4 raw characters ever reach the sink, not
enough to form valid tag syntax, but fixed anyway since the cost was one
line).

**Fix.** `esc()` wrapped at 8 sites across `pages/home/index.ts`,
`pages/my-plan/index.ts`, `pages/team/index.ts`, `pages/shift/index.ts`,
`features/promos/index.ts` — see the diff for exact lines. No new
dependency, no new pattern — the same `esc()` global every other correct
call site already uses.

**Test-infrastructure gap found and fixed as part of verifying these
fixes**: several of the affected pages' jsdom test files
(`home-page.test.ts`, `team-page.test.ts`, `shift-page.test.ts`) stub
`esc` as a **no-op passthrough** (`(s) => String(s ?? '')`) rather than
the real implementation — meaning their existing tests could not have
caught an escaping regression even before this pass, since the stub
never actually escapes anything. (Other files —
`my-plan-page.test.ts`, `promos.test.ts`, `dealers-page.test.ts`,
`plans-bfq-page.test.ts`, `cash-metrics-page.test.ts`,
`schedule-page.test.ts` — already correctly import the real `esc()`
from `src/app/core.js`, from the 20.50.1 documentation-audit XSS pass;
this pass extends that same fix to the three remaining files.) Switched
all three to the real `esc()` and added 6 new regression tests (one per
fixed field/file, using an `<img onerror=...>`/`<script>` payload and
asserting both `querySelector('img'/'script')` finds nothing AND the
escaped entity is visible in the rendered HTML) plus one more in
`promos.test.ts` for the `mask` fix — 7 new tests total, all passing
against the real `esc()` implementation, not a stub that couldn't fail.

**Deliberately not touched**: the CSP `unsafe-inline` trade-off for
`script-src-attr`/`style-src-attr` (already documented, ~265+
`onclick=` handlers and ~400 inline `style=` attributes — a separate,
much larger architectural epic, not a quick win) and the existing
`tests/isolation/security-headers.test.ts` (already covers
`X-Content-Type-Options`/`Referrer-Policy`/`Cache-Control`/
`Permissions-Policy` — left as-is, sufficient for this pass's scope).

## Explicitly deferred (not silently dropped)

Per the brief's own guidance ("лучше полностью закрыть P1 и оставить
документированный P2, чем сделать фиктивные partial fixes"), the
following sections of the 58-section brief were **not** touched this
pass and need a dedicated future release, not a rushed partial fix:

- **CSP tightening** — the `unsafe-inline` trade-off for
  `script-src-attr`/`style-src-attr` remains untouched (see P1-E above)
  — a separate, much larger architectural epic (~265+ `onclick=`
  handlers, ~400 inline `style=` attributes), not something to chip away
  at inside this pass.
- **P1-C/G residual** — a general sweep applying the new distributed
  rate limiter to every remaining rate-limited route, not just the
  credential-verification set covered this pass.
- **All P2 items** from the brief (AI data minimization, DB constraint
  audit, migration hygiene, audit-log integrity review, session-security
  review, `/metrics/system` PII/cardinality review, `check:route-auth`
  classification levels, `docs/security/public-routes.md`, dependency/
  CI/supply-chain audit beyond the `npm audit`/`npm outdated` run
  recorded in the final report, `package:source` script).

None of these were started and then abandoned mid-way — they were not
touched, so there is nothing half-finished to trip over.
