# 006 — Typed API-клиент как отдельный iife-бандл, не полная миграция фронтенда на Vite

**Статус**: принято, реализовано (20.0.0), суперсед частично в 20.11.0
(старт настоящего SPA-переезда — см. README §22, эпоха 20.14+).

## Контекст

Фронтенд (`backend/frontend/js/*.js`) — 20 классических non-module
`<script>`-файлов, делящих одну глобальную область видимости
(порядок подключения важен — есть отдельный smoke-тест именно на это).
Нужен был способ добавить типизированный слой доступа к API, не
переписывая всё разом.

## Решение

Один TypeScript ES-модуль (`frontend/src/api-client.ts`), собираемый
Vite'ом в формате **iife** (не `es`/`umd`) в единый бандл
`frontend/dist/api-client.bundle.js`, подключаемый как обычный
`<script src=...>` перед остальными легаси-файлами. IIFE сохраняет ту же
семантику загрузки, что и классические скрипты — не требует
`type="module"`, не ломает `scripts/smoke-frontend.mjs` (тот матчит
`<script src="...">` жёстким regexp'ом, не учитывающим `type="module"`).

## Альтернативы

- **Полная миграция всего фронтенда на Vite/ES-модули разом** — отклонено
  на старте (20.0.0): `01-core.js` держит расшаренное мутируемое
  состояние (`me`, `adminViewOrgId`, `METRICS`), на которое прямо
  ссылаются все остальные 19 файлов — полная модуляризация была бы
  большим, рискованным заходом без пилота. Вместо этого — узкий слой
  (сеть) сначала, оркестрация/состояние/роутинг позже, отдельным заходом.

## Последствия

- Эпоха 20 (Frontend Foundation, 20.0.0→20.7.0) полностью перевела сетевой
  слой всех 20 файлов на typed-клиент, не тронув DOM/оркестрацию/роутинг —
  честная, узкая граница результата, задокументированная как таковая.
- 20.11.0 констатировал: `pages/`/`features/`/`entities/`/`app/router.ts`/
  `app/state.ts` — это не результат простого перемещения файлов, а
  настоящий SPA-переезд сравнимого размера с самой эпохой 20 — начат как
  отдельный, более длинный проект (см. README §22), не смешан с
  backend/docs-реструктуризацией той же версии.
