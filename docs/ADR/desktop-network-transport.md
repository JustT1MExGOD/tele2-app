## Контекст

Приложение должно подключаться к T2 Sales из сетей, где основной адрес недоступен, без ручного управления VPN или системным прокси. Ограничение проекта: не изменять сеть других приложений, системный DNS, маршруты, файл hosts или параметры Windows.

Записи архитектурных решений хранятся в `docs/ADR/`. Регистр каталога соответствует существующей структуре репозитория; отдельный каталог `docs/adr/` не создаётся.

## Решение

| Транспорт | Когда используется | Как работает |
|---|---|---|
| **DIRECT** | Предпочтительный путь в автоматическом режиме | `BrowserWindow` открывает исходный HTTPS-адрес штатными средствами Electron |
| **RELAY** | Прямое соединение не подтвердилось; relay доступен | Перехват запросов в сессии Electron и передача через сервис `relay/` |
| **WINDOWS_COMPAT** | Возможное будущее расширение после отдельных испытаний | Сейчас `NoopWindowsCompatibilityAdapter`; `isSupported()` возвращает `false` |

### Почему сначала DIRECT

Пользователь получает ту же страницу и сетевое поведение, что в обычном браузере. Для работающего прямого соединения не требуется дополнительный сервис посредника.

### Почему резервный путь ограничен приложением

В режиме RELAY используется `session.protocol.handle`: меняется способ доставки ответа, но страница продолжает работать под исходным origin. Это необходимо для cookies, CSRF и привязки WebAuthn к origin / RP ID.

Выбранный подход даёт следующие свойства:

- **Одна задача:** передавать HTTP-запросы этого приложения одному настроенному серверу.
- **Без системных изменений:** нет правок Windows proxy, DNS, hosts, маршрутов или firewall.
- **Обычные права пользователя:** не нужны драйвер, служба и запуск от администратора.
- **Ограниченная сложность:** HTTP-протокол, разрешённые заголовки и один upstream проще сопровождать, чем обработку сетевых пакетов.
- **Понятное отключение:** достаточно снять обработчик протокола внутри сессии; системное состояние восстанавливать не требуется.

### Почему низкоуровневый адаптер отложен

Реализация на уровне пакетов или Windows Filtering Platform рассматривалась только как крайний вариант. Сначала нужны подтверждённые случаи, в которых недостаточны одновременно DIRECT и RELAY. Локальный тест или успешная компиляция такой необходимости не доказывают.

Интерфейс `NetworkCompatibilityAdapter` оставлен для будущего расширения. Флаг `T2_WINDOWS_COMPAT_ENABLED` по умолчанию выключен; его включение не создаёт отсутствующую реализацию.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Общий SOCKS-прокси | Расширяет область использования за пределы одного приложения |
| Туннель CONNECT | Требует управления доступными адресами и портами; отличается от передачи запросов одному backend |
| TUN/TAP или системный VPN | Добавляет низкоуровневое состояние и выходит за исходные ограничения |
| Изменение глобального Windows proxy | Влияет на другие приложения и усложняет откат |

## Последствия и ограничения

1. RELAY зависит от корректного сохранения cookies, CSRF и WebAuthn при перехвате протокола. Эти сценарии проверяются отдельно, а не выводятся из успешной загрузки страницы входа.
2. Если `protocol.handle` окажется несовместим с WebAuthn, рассмотренный запасной вариант — локальный прокси через `session.setProxy()` только для сессии приложения. Проверки RP ID и origin при этом сохраняются.
3. Доступность relay не гарантирует доступность основного приложения: требуется проверять весь путь и авторизованные операции.
4. Исторические испытания DIRECT → RELAY и обновления не являются автоматическим подтверждением новых функций, например чата.
5. Транспорт не добавляет доверия к клиенту: доступ по-прежнему определяет сервер.
