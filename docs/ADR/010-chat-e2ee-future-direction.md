# 010 — Сквозное шифрование чата: предложение, не реализовано

[Документация](../README.md) · [Обзор проекта](../../README.md)

**Статус**: предложено/запланировано. Дополняет [ADR/008](./008-e2ee-not-implemented.md)
для одного конкретного нового скоупа (внутренний чат сотрудников,
20.57.0) — **не отменяет и не переписывает ADR/008 задним числом**.
ADR/008 остаётся полностью в силе для своего исходного вопроса (общая
1:1-приватная переписка между двумя конкретными сотрудниками) — такой
фичи по-прежнему не существует, вывод ADR/008 по-прежнему верен.

## Почему этот ADR вообще появился, а не только запись в ADR/008

Внутренний чат (`docs/CHAT.md`) сам по себе — **broadcast внутри
организации/сети**, та же категория, что уже перечислена в таблице
ADR/008 (`channels`/`announcements`) — команда с общей видимостью, не
1:1-переписка. По буквальному критерию ADR/008 ("есть ли `recipient_id`/
`participant`/`conversation`") чат сам по себе НЕ создаёт новый triggering
event для E2EE.

Отдельный ADR оправдан не логикой ADR/008, а тем, что владелец продукта
уже неоднократно и явно называл конкретное будущее направление именно для
ЭТОГО чата — hybrid-ratcheting шифрование (PQXDH → ratcheting protocol →
AEAD → зашифрованные вложения) — как часть исходного брифа на сам чат, не
как гипотеза, придуманная при реализации. Фиксировать это отдельно —
не "создать ADR ради количества файлов", а не потерять уже озвученное
продуктовое намерение, которое иначе нигде не записано.

## Решение

Направление зафиксировано как **Запланировано**, ничего не реализовано:

1. **Transport envelope отделён от message content уже сейчас** —
   `chat_messages.content_type`/`chat_messages.encryption_version`
   (`0026_chat.sql`) существуют как нейтральные поля именно для этого;
   `encryption_version` не используется НИ ОДНИМ кодом сегодня — задел,
   не функциональность.
2. **Направление, не спецификация**: PQXDH-класс handshake → протокол
   класса ratcheting (Double Ratchet и его групповые/pairwise варианты —
   **семейство, не выбранная реализация**) → AEAD для тела сообщения →
   тот же принцип для байт вложений (`StorageAdapter` уже не понимает
   содержимого блоба, см. `docs/CHAT.md` — хранить шифротекст вместо
   открытый текст не потребует менять сам адаптер).
3. **Explicitly NOT decided**: конкретная библиотека/протокол-имплементация
   (Signal's libsignal, MLS/RFC 9420, или другое — не выбрано и не
   должно восприниматься как выбранное), конкретные крипто-параметры
   (curve/KEM/AEAD-сюит), формат сериализации ratchet state.
4. **Group vs 1:1**: чат сегодня — один общий канал на сеть (broadcast),
   не 1:1. Зрелые ratcheting-протоколы для GROUP-контекста (Sender Keys,
   MLS) — другая крипто-задача, чем классический Double Ratchet для пары
   собеседников; какой именно применим, не решено этим ADR — только
   называется как открытый вопрос.
5. **Multi-device / device identity — отдельный, нерешённый дизайн-
   вопрос.** Сегодня в проекте нет концепции устройства как отдельной
   криптографической идентичности (см. ADR/008 — то же самое верно и
   здесь). E2EE для чата с несколькими устройствами на сотрудника
   (Telegram + browser + Electron одновременно, что уже реальность для
   этого продукта) требует device-key-каталога/пересылки ключей новым
   устройствам — не спроектировано, не начато.

## Явно НЕ утверждается этим документом

- E2EE **не реализовано** — сегодня сервер видит открытый текст body и
  открытый текст вложения целиком (см. `docs/CHAT.md#privacy`).
- Triple Ratchet/SPQR (или любое другое конкретное название) **не
  выбраны** как production-реализация — упоминались в исходном
  продуктовом брифе как одна из точек на пути, не как принятое решение
  этого ADR.
- Самописная криптография **не будет писаться** — тот же STOP condition,
  что уже применён в ADR/008: зрелая, проверенная библиотека или ничего.
- Никаких крипто-параметров этот документ не фиксирует — фиксировать их
  до выбора конкретной реализации значило бы гадать, а не проектировать.

## Альтернативы

| Вариант | Вердикт | Почему |
|---|:---:|---|
| Молчать про будущее направление, полагаясь только на ADR/008 | ❌ отклонено | ADR/008 отвечает на другой вопрос (нет 1:1-переписки); явно озвученное владельцем продукта направление для ИМЕННО этого чата осталось бы нигде не зафиксированным |
| Реализовать E2EE сейчас, в рамках 20.57.0 | ❌ отклонено | Прямо запрещено текущим брифом; преждевременно — сначала должны быть доказаны auth/realtime/idempotency/attachments/relay/UX на открытый текст-слое (что и сделано в 20.57.0) |
| Зафиксировать конкретные крипто-параметры/библиотеку заранее, «на будущее» | ❌ отклонено | Фиксация без выбора зрелой реализации — гадание, не проектирование; тот же принцип, что уже отклонил «заготовку без протокола» в ADR/008 |
| Задокументировать направление как предложено/запланировано, без реализации и без преждевременных решений | ✅ принято | Сохраняет уже озвученное продуктовое намерение, не создаёт мёртвый крипто-код, оставляет реализацию отдельному будущему заходу с реальным сравнением библиотек |

## Что нужно решить перед реализацией

Ничего из списка ниже не спроектировано этим документом — только названо
как открытый вопрос, чтобы не потеряться при будущей реализации:

- **Group-ratcheting протокол** (MLS/RFC 9420 vs Sender Keys vs другое) —
  сравнение зрелости/доступности библиотек под Node/Electron/browser/
  Telegram WebView одновременно.
- **Device identity** — сегодня в проекте нет концепции устройства как
  отдельной криптографической идентичности (см. п.5 выше и ADR/008).
- **Multi-device key distribution** — как новое устройство сотрудника
  получает доступ к текущему групповому ключевому состоянию; дизайн,
  которого сегодня нет вообще.
- **Recovery** — что происходит, если сотрудник теряет ВСЕ свои
  устройства разом (переустановка телефона и компьютера одновременно,
  потеря доступа к Telegram-аккаунту) — историю чата видно другим членам
  сети, но что видно/восстановимо ли для самого сотрудника, не решено.
- **Key backup** — есть ли вообще backup ключевого материала (и через
  что — тот же вопрос, что recovery, но применительно к самим ключам, не
  к возможности прочитать историю), или каждое устройство — единственный
  держатель своих ключей без резервной копии (компромисс между
  восстанавливаемостью и защита прошлых сообщений при раскрытии текущего ключа, не решён).
- **Group membership changes** — сотрудник присоединяется к
  организации/переводится в другую/деактивируется: нужно ли
  re-keying/rotation группового состояния в эти моменты, кто это
  инициирует, что происходит с уже отправленными сообщениями относительно
  нового/ушедшего участника.
- **Device revocation** — как отозвать скомпрометированное/потерянное
  устройство конкретного сотрудника без затрагивания остальных
  устройств/сотрудников; не нужен без device identity (см. выше), но
  потребуется вместе с ним.
- **Attachment key lifecycle** — вложения хранятся отдельно от текста
  сообщений (`StorageAdapter`, см. `docs/CHAT.md`); если/когда появится
  encryption, ключ для расшифровки конкретного вложения должен быть
  привязан к тому же групповому состоянию, что и текст, без отдельного
  более слабого механизма — как именно, не решено.
- Что происходит с server-side возможностями, которые требуют открытый текст
  сегодня (magic-byte валидация вложений, полнотекстовый поиск, если
  появится) — какие из них становятся невозможны и это осознанно
  принимается, какие переезжают на клиент.
- Явное решение владельца продукта о приоритете (когда, а не "когда-нибудь").
