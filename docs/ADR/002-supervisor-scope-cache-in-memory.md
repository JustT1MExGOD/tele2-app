# 002 — In-memory кэш supervisor scope вместо Redis

**Статус**: принято, реализовано (19.25.0).

## Контекст

`resolveSupervisorStores()` — реальный hot path кабинета супервайзера и
Command Center — на каждую загрузку страницы гонял JOIN
`supervisor_sectors → organizations → stores`. Нужен был кэш, чтобы не
пересчитывать этот JOIN на каждый запрос.

## Решение

In-memory `Map` в процессе (`src/core/shared/scope-cache.ts`), TTL 5 минут,
точечная инвалидация (`invalidate(supervisorId)`) на `PUT
/supervisor/:id/sector` и `PATCH /employees/:id/role`, полная
(`invalidateAll()`) на `PUT /admin/org/:id`.

## Альтернативы

| Вариант | Вердикт | Почему |
|---|:---:|---|
| Redis | ❌ отклонено | Прод — 1 реплика Railway; `grammy`-бот на long-polling физически не живёт на двух инстансах одного `BOT_TOKEN` без `409 Conflict` от Telegram API — горизонтальное масштабирование уже исключено другим компонентом системы, не только этим кэшем. Новый managed-сервис + новый сетевой failure mode (Redis недоступен → что с кэшем?) без выигрыша в корректности при одной реплике |
| In-memory `Map`, TTL 5 мин | ✅ принято | При одной реплике даёт ровно ту же корректность, что Redis, без лишней инфраструктуры |

## Последствия

- **Триггер пересмотра**: переход прод-сервиса на несколько реплик — что
  само по себе требует сначала перевести бота с long-polling на webhook
  (отдельный, более крупный переход). До этого момента вводить Redis ради
  одного кэша — новая инфраструктура без пропорциональной выгоды.
- `GET /admin/cache-stats` (admin-only) — `{hits, misses, size, hitRate}`,
  ops/debug-метрика для проверки эффективности кэша на практике, не
  отдельный UI-экран.

## Обновление (уточнение, обнаружено документационным аудитом v20.50.0+)

Кэш обслуживает не «супервайзерский scope» в общем, а конкретно
`resolveSupervisorStores()` (`core/analytics/supervisor.ts`) — hot path
кабинета супервайзера и Command Center, ровно то, для чего он и
проектировался. Общая функция фильтрации по сектору для остальных роутов,
`getUserStoreIds()` (`auth/guards.ts`), ходит в
`supervisorSectorsRepo.listStoreIdsForSupervisor` **напрямую**, минуя кэш.
Это не расхождение/баг: у двух путей разная частота вызова, и раз кэш —
не единственный источник данных (fallback на прямой запрос уже был
частью решения), расхождение TTL между ними структурно невозможно —
`getUserStoreIds()` просто всегда видит актуальные данные. Стоит знать
при отладке "почему это конкретное место не подхватило инвалидацию кэша
мгновенно" — оно и не должно было, кэша там нет.
