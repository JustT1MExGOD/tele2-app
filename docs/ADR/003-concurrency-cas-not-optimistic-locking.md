# 003 — CAS/unique-constraint concurrency вместо optimistic locking

**Статус**: принято, подтверждено аудитом (19.24.0).

## Контекст

Ревью безопасности поставило вопрос: нужна ли системная схема
optimistic locking (версионирование строк, `WHERE version = $expected`)
для защиты от гонок и lost-update сценариев по всему backend?

## Решение

Перед тем как писать новый код, проведён аудит того, что уже реально
защищено — оказалось, большая часть механизмов конкурентности уже
существовала с эпохи 17.0, просто не была закреплена тестами, которые
реально стреляют параллельно:

- `idx_shift_sessions_one_open_per_employee` — partial UNIQUE INDEX,
  физически не даёт двух открытых смен одному сотруднику.
- Закрытие смены — `UPDATE ... WHERE id=$X AND status='open'`, честный
  compare-and-swap (не read-then-write).
- `offline_sync_log.client_id` — настоящий UNIQUE constraint +
  `ON CONFLICT DO NOTHING`, идемпотентность на уровне схемы, не только
  в коде.
- `sales` — `UNIQUE(employee_id, store_id, sale_date)`.

Найдена и закрыта ровно одна настоящая гонка —
`materializeStoreDailyPlans()` (delete-then-insert без `ON CONFLICT` и
без уникального constraint'а на `(store_id, plan_date)`, вызывался и
кроном в 6:00, и синхронно из PUT-эндпоинта) — исправлено добавлением
`UNIQUE(store_id, plan_date)` (миграция 0013) + per-store `INSERT ... ON
CONFLICT DO UPDATE`.

## Альтернативы

- **Optimistic locking (версионирование строк) по всему backend** —
  отклонено: `PATCH /stores/:id` и подобные эндпоинты уже делают
  частичный `UPDATE SET <только присланные поля>`, не перезапись всей
  строки — классический lost-update сценарий (A читает всю строку, B
  меняет поле, A перезаписывает всей своей копией, затирая правку B)
  физически не возникает при таком паттерне UPDATE. Добавлять
  версионирование под гипотетическую, не обнаруженную на практике
  проблему означало бы новую сложность (версия в каждой таблице, разбор
  409-конфликтов на фронте) без реального риска, который она бы закрывала.

## Последствия

- Каждый из найденных механизмов закреплён adversarial-тестом, реально
  стреляющим `Promise.all()` из двух одновременных запросов, а не
  проверяющим последовательные сценарии — иначе регрессия на этот класс
  багов осталась бы незамеченной.
- Проверять «уже ли защищено» перед тем, как писать новую защиту, стало
  повторяемым паттерном для этого проекта — избегает и дублирования
  существующих гарантий, и false confidence от нового кода поверх уже
  надёжного.
