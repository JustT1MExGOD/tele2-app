# Contributing

> Текущая практика проекта, не аспирационный шаблон — здесь описано, как
> реально ведётся разработка сейчас, чтобы новый человек не удивлялся,
> почему нет PR-шаблона или веток `feature/*`.

## Как сейчас

Один активный мейнтейнер, коммиты идут напрямую в `main` — без
promotional-веток и review-процесса, но **не** без дисциплины: каждый
коммит перед пушем проходит одну и ту же проверку (см.
[DEVELOPMENT.md — соглашения](./docs/DEVELOPMENT.md#соглашения)):
типизация, `smoke:frontend`, полный `vitest run` на одноразовом локальном
Postgres. Если появится второй контрибьютор — этот раздел обновится под
PR-флоу, переписывать заранее «на будущее» не стали.

## Если контрибьютишь

- **Ветки**: пока не обязательны для одного мейнтейнера; если работаешь
  параллельно с кем-то ещё — `<имя>/<короткое-описание>`, мёрж в `main`
  через PR с зелёным CI.
- **Коммиты**: один коммит — одна логическая правка. Сообщение — что и
  зачем, не только что; версия в первой строке для сущностных правок
  (`20.NN.0: fix: ...`), см. существующую историю в `git log` как образец
  тона.
- **Перед любым коммитом**:
  1. `npx tsc --noEmit` — чисто
  2. Если менялся `frontend/src/` — `npm run build:frontend`
  3. `npm run smoke:frontend`
  4. `npm run test:frontend` (если есть фронтенд-тесты для затронутого)
  5. Полный `npx vitest run` на **локальном** одноразовом Postgres — никогда
     на общей/прод БД (`tests/setup.ts` это принудительно проверяет)
- **Не коммитить**: `.env`, любые файлы с реальными секретами
  (`DATABASE_URL`, `BOT_TOKEN`), файлы из `frontend/dist/` (собираются на
  деплое, не хранятся в репозитории)
- **Версионирование** (см. `CLAUDE.md`): MINOR на каждую сущностную
  правку (фича/фикс/рефакторинг), changelog-запись в
  `src/platform/notifications/changelog.ts` только для эпиков, не для
  хотфиксов — история версий в [CHANGELOG.md](./CHANGELOG.md) полнее, чем
  changelog-анонсы в Telegram
- **Данные БД**: изменение схемы — только новый файл в
  `backend/migrations/`, никогда ad hoc SQL на Railway напрямую (см.
  [DEVELOPMENT.md](./docs/DEVELOPMENT.md), [RUNBOOK.md](./docs/RUNBOOK.md))

## Прежде чем писать код

- Роли/доступ — прочитать [SECURITY.md](./docs/SECURITY.md), особенно §3
  (RBAC) — самый частый класс прошлых багов в этом проекте именно здесь
  (org-scope, роль).
- Структура — [ARCHITECTURE.md](./docs/ARCHITECTURE.md): `api → core →
  data`, доступ к Postgres только через `data/repositories/*`
  (`npm run check:no-direct-sql` проверяет это в CI).
- Не переизобретать — сначала `grep` по `docs/ADR/`, возможно решение уже
  обсуждено и осознанно отклонено.

## Вопросы / баги

Один мейнтейнер — issues GitHub не используются как основной канал.
