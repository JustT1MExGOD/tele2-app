## Как применить

1. Содержимое папки `tele2-app-main` из ZIP скопировать в корень актуального проекта с заменой файлов. Остальные файлы проекта нужны и остаются на месте. Удалений в пакете нет.
2. В `backend` использовать Node.js 22, выполнить `npm ci`, затем `npm run build`.
3. Обязательна миграция `backend/migrations/0027_functional_integrity.sql`. Штатный запуск приложения применяет миграции автоматически; отдельный штатный запуск — `npm run migrate` с подключением к нужной БД. Перед обновлением нужна восстанавливаемая резервная копия БД. Не запускать тесты на рабочей БД.
4. Обновить backend и frontend совместно. Архив содержит исходники, а не `dist` или `node_modules`.
5. Для desktop выполнить `npm ci` и `npm run desktop:build`; Windows-инсталлятор собирается штатной командой проекта в Windows-среде.
6. После установки проверить одну продажу, повтор того же запроса, открытие/закрытие смены, календарь, CSV и обмен сообщениями между двумя экземплярами backend. Это проверки установки, а не выполненные здесь production-проверки.

Миграция добавляет канонические результаты синхронизации и закрытия смен, снимок плана, журнал заданий отчётов, дату последней смены, два индекса чата и недостающие столбцы пользовательских метрик в месячных планах точек. Старые файлы миграций не изменены. Новые индексы создаются внутри обычной транзакции: на большой рабочей таблице создание может ожидать блокировки; длительность здесь не измерена. Параллельные процессы применения миграций сериализуются advisory lock.

## Производительность и интерфейс

- Сводки сотрудников, точек и общий BFQ получают данные пакетами. Число запросов основных наборов данных больше не растёт как четыре запроса на каждого сотрудника. В сводке сотрудников используются пять пакетных запросов; холодный кэш каталога требует дополнительных обращений.
- Изменение месячного плана точки пересчитывает только эту точку своей организации на сегодня/завтра в применимом месяце. Неизменившиеся материализованные строки не переписываются.
- Фоновое расписание читает конфигурации точек без загрузки каждого плана на каждом минутном тике. План загружается при выполнении задания.
- Продажи экспортируются потоком, страницы по 500 строк. Пользовательские метрики включены. Это не фиксированный снимок всей БД: правки во время долгой выгрузки могут отразиться в последующих страницах. Relay по-прежнему может буферизовать ответ.
- Чат хранит/рисует окно до 300 канонических сообщений. История загружается страницами; после ухода в старую историю переход к новым сообщениям повторно получает актуальную страницу. Ожидающие отправки отображаются отдельно.
- Межрепличная доставка ограничена двумя параллельными чтениями и 100 ожидающими уведомлениями на процесс. При перегрузке или потере NOTIFY сообщения восстанавливает REST. Клиент дочитывает максимум десять страниц за один проход и продолжает следующим проходом, не пропуская остальные страницы.
- Офлайн-очередь имеет один выполняющийся flush, отправляет максимум 50 операций за запрос, переиспользует соединение IndexedDB, сохраняет ошибочные операции и увеличивает паузу повторов. В интерфейсе появилась кнопка количества неподтверждённых записей и окно с ошибками/повтором. Окно показывает первые 100 записей, остальные остаются сохранёнными.
- Шрифты: **2 065 176 → 183 896 байт**, уменьшение примерно **91,1%**. Сохранены латиница, кириллица, греческий и основные знаки. Для остальных письменностей используется системный резервный вариант. Это измерение файлов шрифтов, а не ускорение всей страницы на 91%.

## Настройки для БД 8 vCPU / 8 GB

Добавлены настройки приложения:

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `PG_POOL_MAX` | 8 | Максимум соединений обычного пула на процесс |
| `PG_CONNECT_TIMEOUT_MS` | 5000 | Ожидание соединения |
| `PG_STATEMENT_TIMEOUT_MS` | 30000 | Ограничение SQL-запроса |
| `PG_IDLE_TRANSACTION_TIMEOUT_MS` | 30000 | Ограничение простаивающей транзакции |
| `CHAT_LISTEN_DATABASE_URL` | `DATABASE_URL` | Прямое подключение для LISTEN; нужно отдельно при transaction-pooling |

У каждого экземпляра backend дополнительно **одно** соединение LISTEN. Для двух экземпляров при стандартных настройках получается до **18** соединений приложения, плюс миграции, администрирование и другие потребители. Размер пула не умножается автоматически на число vCPU. Начинать с этого небольшого бюджета и менять его по измерениям ожидания, CPU, I/O и p95, а не просто увеличивать `max_connections`.

Добавлены Prometheus-метрики `db_pool_total`, `db_pool_idle`, `db_pool_waiting`. Существующие метрики SQL/HTTP и заданий сохранены. У конфигурации PostgreSQL нет универсального «идеала» только по двум характеристикам оборудования: параметры памяти, autovacuum и параллелизма требуют размера таблиц, диска, планов запросов и реального профиля нагрузки. Рабочий PostgreSQL здесь не перенастраивался.

## Важные границы нового поведения

- У старых `offline_sync_log` нет канонического результата. Повтор такой операции возвращает **409 для сверки**, а не молча считается доказанно применённым. Нельзя автоматически восстановить потерянную старую продажу по одному существованию ключа или удалить ключ и повторить её: это может задвоить уже сохранённые данные.
- Доставка Telegram — **at-least-once**. Если Telegram принял сообщение, а процесс умер до записи результата, повтор может отправить его снова. Lease/транзакция БД не дают exactly-once для внешнего API. Напоминания нескольким сотрудникам и story из нескольких сообщений также могут быть частично отправлены до ошибки.
- У отчётного задания до пяти попыток с задержкой; после исчерпания оно остаётся `failed` в `report_jobs`, с `last_error`. Автоматического бесконечного повтора и отдельного экрана ручного управления заданиями нет. Уже поставленные задания переживают перезапуск; дни, в которые приложение вовсе не запускалось и ничего не поставило в очередь, автоматически целиком не восстанавливаются.
- Микроотчёт при задержке помечает плановое время и использует данные на момент отправки; это не восстановленный исторический снимок на конкретную минуту.
- Снимки плана и закрытия появляются для новых смен. Существующие закрытые смены не переписываются задним числом. Поздняя продажа меняет текущий факт/аналитику, но не старую выданную награду или сохранённый результат закрытия.
- Списание ранее начисленного XP при отрицательной корректировке не введено: необходима политика для старых продаж, часть которых вообще не получала XP. Базовые веса BFQ и наград не переизобретались.
- Массовый график по-прежнему может пропускать элементы, не прошедшие существующие проверки принадлежности: `count` показывает принятые изменения. SQL-ошибка откатывает всю транзакцию. Контроль одновременного редактирования через версию/ETag не добавлен.
- Сохранение исторических итогов при деактивации исправлено. Полная история переводов сотрудника/точки между организациями требует отдельной модели принадлежности во времени.

## Что из рекомендаций аудита осталось отдельной работой

Это существенный набор исправлений, **не утверждение, что реализованы все предложения аудита или найдены все возможные ошибки**.

1. **Файлы чата вынести из основной БД.** Нужны выбор объектного хранилища, конфигурация, политика хранения и перенос существующих bytea с проверкой ссылок. В этом пакете bytea не переносится и данные не удаляются.
2. **Закрытие периода и версии бизнес-правил.** Нужны утверждённые веса BFQ, политика возврата XP, правок закрытой смены, разменного остатка и переноса истории между сетями. Снимок нового закрытия — только первый слой.
3. **Остальные N+1 и кэш агрегатов.** BFQ и месячные сводки переведены на пакетные данные. What-if coverage, часть профилей/AI и других аналитических цепочек ещё требуют отдельных пакетных запросов. Готовые агрегаты с явной давностью и событийной инвалидацией не введены повсеместно.
4. **Единое состояние «нет данных / ошибка / устарело».** Нужен согласованный контракт для оставшихся dashboard/health/forecast резервный вариант; устранены только затронутые пути. Общий перерасчёт health score не выполнялся.
5. **Полный UI/UX-проход.** Сохранены свежие модальные улучшения; исправлен редактор смены, добавлено состояние очереди, ограничен чат. Не выполнены полный перевод оставшихся prompt/confirm в формы, новая ролевая домашняя страница, сохранение всех фильтров/черновиков, полевой accessibility-аудит и сценарий 30–60 минут на реальных устройствах.
6. **Новые продуктовые функции** из раздела предложений: сценарии согласования, центр управления заданиями/операциями, расширенное объяснение начислений и полный инструментарий сверки. Они не заменены заглушками и не представлены как готовые.
7. **Ёмкость 8 GB.** Нужны `EXPLAIN (ANALYZE, BUFFERS)` на копии реальных данных, проверка p95/p99 при двух репликах, планы autovacuum/retention, размеры индексов, нагрузка вложений и relay. Изменён код уменьшения нагрузки, но «идеальная конфигурация» без этих измерений не установлена.

Финальная дополнительная проверка чата и целостности: 25 тестов пройдены; финальный транспорт: 8 тестов пройдены. В четырёх шрифтах отдельно проверены русские/латинские символы, рубль и сохранность лицензионных записей.
