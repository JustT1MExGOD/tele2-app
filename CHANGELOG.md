## 20.78.2 — Miranda: корректные числовые ID в JSON-ответах устройств

- Исправлен wire-контракт `/miranda/devices/register`, `/miranda/devices/activate` и `GET /miranda/devices`: `deviceId`, `corporateAccountId`, `binding_id`, `device_id` и `employee_id` теперь сериализуются числами, а не строками PostgreSQL; нативный клиент Miranda снова может разобрать успешный ответ активации.
- Тесты дополнительно фиксируют, что activation-response отдаёт `corporateAccountId` именно JSON number.


- Исправлен хотфикс для устройств, зарегистрированных до 20.78.0: сохранённая `pending`-привязка личного аккаунта теперь автоматически активируется при следующем `/activate`, поэтому повторный вход не требует повторной регистрации или ручного approve.
- Для активированной привязки одновременно устанавливается `active_corporate_account_id` текущей сессии и записывается аудит `MIRANDA_DEVICE_AUTO_APPROVED`; аккаунты точки/кассы (`device_exclusive`) по-прежнему остаются в очереди администратора.
- Добавлен изоляционный регрессионный тест полного сценария старого устройства.


- `GET /miranda/accounts` и `GET /miranda/devices` показывали только свою сеть — аккаунты и устройства соседних сетей дилера были невидимы нигде; теперь скоуп — вся дилерская группа (как `/miranda/contacts/all`), `org_id` продолжает выбирать, какая сеть считается «своей» для дилерской группы.
- Первое устройство личного аккаунта auto-approve: `registerDevice` для не-`device_exclusive` аккаунта без активных привязок создаёт байндинг сразу `active` — вход в Miranda больше не требует второго админа, профиль появляется сразу. Аккаунты точки/кассы (`device_exclusive`) и второе+ устройства по-прежнему идут через pending-очередь.
- Фронтенд Admin Center: `adminListMirandaDevices` и `adminListMirandaCorporateAccounts` теперь передают `org_id` (org-switcher-aware), нативный клиент Miranda получает весь дилер автоматически (backend сам резолвит группу по `org_id`).
- Изоляционные тесты `miranda-accounts` переписаны под новую модель: личный аккаунт → auto-active, exclusive → pending, список аккаунтов/устройств → дилерский скоуп. 10/10.

## 20.77.1 — Fix: admin не мог назначить роль сотруднику переключённой сети

- `PATCH /employees/:id/role` и `POST /admin/employees/:id/role` не передавали `org_id` — admin, переключившийся на другую сеть через org-switcher и пытавшийся назначить роль (в т.ч. `admin`) сотруднику этой сети, получал 403 «Сотрудник не принадлежит вашей сети» (`requireEmployeeInOrg` сверял сотрудника с сетью **активного** admin'а, а не переключённой).
- Исправлено в обоих путях: `setEmployeeRole` (Team page → applyRoleChange) и `adminChangeEmployeeRole` (Admin Center → Сотрудники → onChangeRole) теперь передают `adminViewOrgId` в body.
- Изоляционный тест `roles-sectors` покрывает именно этот сценарий — 8/8 (admin назначает `role: 'admin'` сотруднику `orgB` с `org_id: orgB` → 200).

## 20.77.0 — Перенос точек, native-топы, Miranda cookie-fix, заявки на доступ, компактный switcher

- Перенос точки между сетями/дилерами: `POST /admin/stores/:id/move` существовал на backend с 20.72.0, UI не было нигде — добавлено поле `org_id` сети-получателя и кнопка «Перенести» на вебе (Admin Center → Точки → деталь) и в нативном клиенте, с подтверждением через dangerous-action диалог.
- Заявки на доступ стали org-switcher-aware: `getAccessRequests`, `approveAccessRequest`, `rejectAccessRequest` не передавали `org_id` — список молча показывал только свою сеть, approve/reject заявки другой сети падали 403 (тот же класс бага, что у «Точек» в 20.76.0).
- Критический баг Miranda: `FileCookiesStorage` у T2 Sales и Miranda писал в один файл `~/.t2sales/cookies.json` — T2 Sales перезаписывал сессию Miranda при любом своём запросе (разные процессы, last-writer-wins), аккаунт точки «вылетал» при входе в T2 Sales на той же машине; Miranda переведена на отдельный `miranda-cookies.json`.
- Native: экран «Топы» в сайдбаре (`Screen.Leaderboard`, иконка трофея), `LeaderboardApi` с `org_id`-поддержкой, период-пикер, табы по каталогу метрик, прогресс-бары — паритет с веб-версией 20.75.0.
- Веб: org-switcher из блока трёх полноразмерных select переделан в компактную «таблетку» рядом с кнопками шапки — по клику открывается попап с каскадным Дилер→Сектор→Сеть, как `NetworkIndicator.kt` в нативном клиенте.
- tsc --noEmit (backend+frontend), vitest 942/942 (backend, одноразовый Postgres) + 692/692 (frontend), check:route-auth, check:architecture, check:inline-event-handlers (baseline 306→303), check:frontend-architecture, check:frontend-legacy-globals, build:frontend, smoke:frontend, compileKotlin (desktopApp/mirandaApp/androidApp) — без регрессий.

## 20.75.0 — Топы сотрудников: отдельная вкладка, прогресс-бары по каждой метрике

- Новая вкладка «Топы» в основной навигации — видно ВСЕМ ролям (не только manager/admin/supervisor, как у существующего сводного топа в кабинете супервайзера), своя сеть по умолчанию или сеть, на которую переключился admin (`org-switcher`, 20.73.0).
- Отдельный топ по КАЖДОЙ метрике каталога отдельно (SIM, аксессуары, телефоны, MNP и т.д.) — не один сводный score; работает автоматически для новых метрик каталога, без правок кода на каждую: `GET /leaderboard?metric=<id>&from=&to=`.
- Период — явный выбор диапазона дат (два `<input type="date">`), по умолчанию 1-е число текущего месяца → сегодня (Europe/Moscow).
- Метрика хранится в одном из двух физических мест (реальная numeric-колонка `sales` или EAV-таблица `sale_metric_values`) — новый `findEmployeeLeaderboard` в DAL резолвит это прозрачно для вызывающей стороны.
- Попутный фикс реальной латентной ошибки: `getMetricDefs()` (единый каталог метрик) раньше терял базовые метрики (`sim`/`mnp`/`pa`/...) из каталога целиком, как только в `plan_metrics` появлялась хотя бы одна кастомная метрика — теперь базовые метрики всегда присутствуют независимо от того, что в БД.
- tsc --noEmit (backend+frontend), vitest 941/941 (backend, одноразовый Postgres) + 683/683 (frontend), check:route-auth, check:architecture, build:frontend, smoke:frontend — без регрессий.

## 20.72.0 — Глобальная админка + дилеры/секторы: создание и перенос точек

- Админка стала по-настоящему глобальной: единственный администратор теперь управляет ЛЮБОЙ сетью любого дилера, не только своим дилером — Miranda-роуты (`GET/POST /miranda/accounts`, мутации `/miranda/groups`) приведены к тому же паттерну, что уже давно используют остальные Admin Control Center роуты (`resolveViewOrgId`, без проверки принадлежности дилеру).

## 20.71.0 — T2 Miranda: администрирование аккаунтов — тоже в рамках дилера

- `GET/POST /miranda/accounts` — единственный админ дилера теперь видит и может создавать корпоративные/точечные аккаунты в ЛЮБОЙ сети своего дилера (явный `orgId` в теле запроса, провалидированный по `resolveDealerOrgIds`), не только в своей собственной; без `orgId` — прежнее поведение (своя сеть).
- Пересмотр решения из 20.70.0 — там администрирование аккаунтов намеренно осталось per-org; на практике единственный существующий админ не может создать аккаунт в новой сети своего же дилера без второй учётной записи, что и было вскрыто при массовом заведении точечных аккаунтов «Мск-Точки».
- Попытка указать `orgId` вне своего дилера — явный 403 `forbidden`.
- tsc --noEmit (backend), vitest 930/930 (backend, одноразовый Postgres, новый тест на дилер-скоуп администрирования аккаунтов), check:route-auth, check:architecture — без регрессий.

## 20.70.0 — T2 Miranda: видимость контактов/групп/переписки в рамках дилера

- Контакты, группы контактов и диалоги мессенджера T2 Miranda больше не изолированы строго по одной сети — теперь видны и доступны в рамках всего дилера (сотрудники разных организаций одного дилера видят друг друга, могут переписываться и состоять в общих группах контактов); реализовано через `core/orgs/dealers.ts::resolveDealerOrgIds(orgId)`, без новых таблиц/миграций — переиспользует существующую схему `dealers → sectors → organizations.sector_id`.
- Сети без сектора/дилера не затронуты вообще (fallback `dealerOrgIds = [orgId]`) — все существующие org-isolation гарантии Miranda сохранены там, где дилер не настроен.
- Администрирование корпоративных аккаунтов (Admin Control Center) осознанно осталось строго по своей сети — расширена только видимость контактов/групп/переписки, не управление аккаунтами.
- tsc --noEmit (backend), vitest 929/929 (backend, одноразовый Postgres, включая новый isolation-тест `miranda-dealer-scope.test.ts` на видимость в рамках дилера и изоляцию между разными дилерами), `check:route-auth`, `check:architecture` — без регрессий.

## 20.69.0 — T2 Miranda: группы контактов становятся общими для сети и вложенными

- Пересмотр по фидбэку после 20.68.0: группы контактов больше не личный контакт-лист каждого аккаунта — теперь это общая для всей сети разметка, которую настраивает администратор (создание/переименование/удаление/состав — только `requireAdmin`), читают дерево все (сотрудники и точечные аккаунты) через `GET /miranda/groups`.
- Вложенность — группа внутри группы (`parent_group_id`, `ON DELETE CASCADE`): `POST /miranda/groups` принимает необязательный `parentGroupId`, дерево контактов рендерит произвольную глубину вложенности с отступами.
- Исправлены два бага из фидбэка: переименование группы теперь сразу видно (раскрытие группы в UI ключуется стабильным id группы, а не отображаемым именем, которое менялось при рендейме), раскрытие/скрытие групп работает корректно на любой глубине дерева.
- Новая миграция `0044_miranda_contact_groups_shared_nested.sql` (поверх уже живой 0043): `owner_corporate_account_id` → `created_by_employee_id` (аудит, не владение) + `parent_group_id`; сиблинги по имени не дублируются (partial-уникальные индексы, совместимо с Postgres < 15).
- tsc --noEmit (backend), vitest 927/927 (backend, на реальном одноразовом Postgres, включая переписанный isolation-тест на вложенные группы и admin-only мутации), native mirandaApp compileKotlin, визуальная проверка окна (иконка, вкладки, дерево контактов) — без регрессий.

## 20.62.0 — двусторонняя синхронизация графика с Google Таблицей

- Обратное направление к 20.61.0: правка графика внутри приложения (обычное сохранение, admin-коррекция, привязка «Замены» к реальной точке при открытии смены) теперь толкается в Google Таблицу через Sheets API (сервис-аккаунт, новый `GOOGLE_SHEETS_SA_KEY_BASE64`/`GOOGLE_SHEETS_SPREADSHEET_ID`) — не только таблица применяется в приложении, но и наоборот.
- Правило приоритета снято полностью: раньше правка в приложении навсегда защищала ячейку от таблицы; теперь обе стороны равноправны — побеждает тот, кто правил последним, в любую сторону, без ping-pong (толкает наружу только app-side писатель, приём правки из таблицы никогда не запускает пуш обратно).
- Новый сотрудник, которого ещё нет в листе, при первой же правке в приложении получает новый блок строк в конце листа автоматически (объединённая ячейка ФИО, служебные подписи по образцу существующих строк).
- Разовый backfill-скрипт (`backend/scripts/sheet-export-backfill.ts`) переносит уже существующий график (с сентября 2026 по умолчанию) в таблицу.
- Намеренно не толкают изменения в таблицу (объёмные пути, риск упереться в квоту Sheets API): массовая генерация графика на месяц (schedule-generator APPLY) и очистка будущих смен при деактивации сотрудника — досогласовать вручную/через backfill.
- tsc --noEmit (backend+frontend), vitest 898/898 (backend, включая новые unit-тесты чистых функций экспорта и переписанные isolation-тесты на симметрию приоритета, на реальном одноразовом Postgres), все security/architecture guardrail-проверки — без регрессий.

## 20.61.0 — импорт графика из Google Таблиц (с сохранением приоритета правок внутри приложения)
